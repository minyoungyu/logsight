# F5 서버의 신분증 — 풀이 (예시)

처음엔 F5가 "클라우드" 카테고리라길래 뭔가 거창한 걸 상상했는데, 결국은 관리자 페이지에 있는
작은 기능 하나 때문이었다. 순서대로 적어본다.

## 1. 정찰 — 관리자 페이지부터 들어가야 했다

바이트마트 사이트를 그냥 눌러보다가 `/admin/` 으로 가봤더니 로그인 화면(`/admin/login.php`)이 떴다.
F5 설명에 "관리자만 쓸 수 있는 기능"이라는 뉘앙스가 있어서, 일단 관리자로 들어가는 게 먼저겠구나 싶었다.
관리자 로그인은 F2에서 이미 뚫어둔 상태였다. (F2 안 풀었으면 여기서 막혔을 듯. 나는 F2에서
`admin' -- ` 로 로그인 우회가 됐었다.)

[스크린샷 1: 관리자 대시보드 들어간 화면]

사이드바에 메뉴가 세 개 있었는데 그중 "외부 이미지 가져오기"(`/admin/fetch.php`)가 눈에 띄었다.
URL 넣으면 서버가 대신 받아서 보여준다는 설명. 이거 서버가 "대신" 요청을 보내준다는 거면 SSRF 냄새가 났다.

## 2. 가설 — 서버가 대신 요청하면, 내부 주소도 되지 않을까

가설은 단순했다. 이미지 URL 자리에 외부가 아니라 **서버 내부 주소**를 넣으면, 서버가 자기 입장에서
그 주소로 요청을 보낼 거다. 클라우드(AWS로 추정)면 인스턴스 메타데이터 주소
`169.254.169.254` 가 뚫릴 수도 있다. 실제로 도움말에 그 주소가 예시로 적혀 있어서 "대놓고 여기로 가라는 건가" 싶었다.

## 3. 시도 — 여기서 좀 헤맸다

**실패 1.** 욕심내서 바로 `file:///etc/passwd` 를 넣어봤다. 서버 파일 읽히면 개꿀이지 싶어서.
결과는:

```
http/https 주소만 가져올 수 있습니다.
```

`file://` 같은 스킴은 막아뒀더라. 아 그렇지, 이건 이미지 가져오는 기능이지.

**실패 2.** 그럼 메타데이터 중에 제일 민감한 부팅 스크립트부터 보자 싶어서
`http://169.254.169.254/latest/user-data` 를 넣었다. 뭔가 비밀번호 같은 게 나오길 기대했는데:

```
이 메타데이터 경로는 열람할 수 없습니다.
```

403이 떴다. user-data 랑 dynamic/ 쪽은 막아둔 모양. (나중에 안 건데 이게 의도된 제한이었다.
운영진이 비밀 못 빼가게 해둔 듯.) 여기서 "아 이거 그냥 전부 막혔나?" 하고 잠깐 접을 뻔했다.

**실패 3.** 내 노트북 브라우저에서 직접 `http://169.254.169.254/...` 쳐봤다. 당연히 안 됨.
링크로컬 주소라 내 PC에서는 못 간다. 이 요청은 **서버가** 보내야 의미가 있다는 걸 다시 깨달았다.

## 4. 성공 — meta-data 쪽은 열려 있었다

막힌 건 `user-data` / `dynamic/` 이었고, `meta-data` 트리는 멀쩡했다. 그래서 차근차근 타고 들어갔다.
fetch 기능 URL 칸에 이걸 넣었다:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

응답으로 역할 이름 하나가 딱 떨어졌다:

```
ctf-t0X-example0000rolename
```

[스크린샷 2: fetch 결과로 역할 이름이 보이는 화면]

F5 문제 이름이 "서버의 신분증"이었던 걸 생각하면, 이 **인스턴스 역할 이름**이 곧 신분증이고 답이구나 싶었다.
제출해보니 맞았다.

> 내가 받은 F5 플래그: `ctf-t0X-example0000rolename` (팀마다 다름. 실제 값은 마스킹)

## 5. 덤 — 여기서 F6로 이어진다는 힌트

역할 이름을 알았으니 그 뒤에 이름을 붙여봤다:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/ctf-t0X-example0000rolename
```

그랬더니 임시 자격증명(AccessKeyId / SecretAccessKey / Token)이 JSON으로 나왔다.

```json
{"Code":"Success","AccessKeyId":"ASIA...(마스킹)","SecretAccessKey":"...(마스킹)",
 "Token":"...(마스킹)","Expiration":"...","Type":"AWS-HMAC"}
```

이건 F6(클라우드 금고)로 가는 열쇠였다. F5는 역할 이름까지가 답이고, 이 키로 S3를 여는 건 F6에서
이어서 했다. (F6 풀이는 따로 적음.)

## 6. 배운 점 / 이게 실무면 어떻게 막나

- 사용자가 준 URL을 서버가 그대로 가져다 요청하면 SSRF가 된다. 특히 클라우드에선 `169.254.169.254`
  메타데이터가 바로 자격증명 유출로 이어진다. 이번엔 `user-data`/`dynamic`은 막혀 있었지만
  `meta-data/iam` 이 열려 있어서 역할·키가 샜다.
- 막는 방법으로 알아본 것: ① 가져올 수 있는 주소를 허용 목록(정해진 이미지 도메인)으로만 제한,
  ② 사설·링크로컬 대역(169.254.0.0/16, 127.0.0.0/8, 10/8 등)으로 가는 요청 자체를 거부,
  ③ 근본적으로는 IMDSv2(토큰 필요)로 올려서 단순 GET SSRF로는 메타데이터를 못 읽게 하는 것.
- 탐지 쪽에서 보면, fetch 요청이 전부 웹 로그(요청 본문 포함)에 남아서 "관리자 기능이 갑자기
  169.254.169.254 를 때리는" 패턴으로 잡을 수 있다. 평소엔 절대 안 일어나는 요청이니까.

## 재현 요약 (채점/검증용)

1. F2로 관리자 로그인 → `/admin/fetch.php` 접속
2. URL 칸에 `http://169.254.169.254/latest/meta-data/iam/security-credentials/` 입력
3. 응답으로 나온 역할 이름이 F5 플래그
4. (이어서) 역할 이름을 뒤에 붙이면 임시 키가 나옴 → F6로 연결
