# 클라우드 공방전 로그로 측정한 결과 (규칙만, AI 없음)

측정일 2026-10-26 · 대상 2026-10-11 공방전(EC2·EKS·Lambda) · 정답지 블루팀 최종 보고서(2026-10-12)

## 한눈에 보기

- LogSight는 이 공방전의 핵심 공격 경로를 **하나의 사건(INC-002)으로 묶었다.** 14:10의 웹앱 내부 주소 조회 시도(WAF 차단)와
  15:36~16:08에 EC2 역할 임시 키를 외부 IP에서 쓴 기록(워크플로 실행 9건, SSM 시도 4건)이 같은 공격자 IP로 이어졌다.
  블루팀이 보고서에 적은 "웹 → 키 탈취 → 외부 사용" 흐름과 같다.
- 하지만 이 사건은 **2위**였다. 1위는 블루팀 자신의 조회 작업(432건)을 "계정 정찰"로 본 오탐이었다.
- 입력 데이터에 있는 공격 6단계 중 **5단계를 표시**했다. PageSnap 결과 PDF 내려받기는 놓쳤다.
- 공격 9단계 중 3단계는 **입력 데이터에 아예 없다.** 통합로그의 CloudTrail(event_history)이 us-west-1 관리 이벤트만,
  16:25까지만 담고 있어서다. 이 부분은 탐지 도구가 아니라 로그 수집 범위의 문제다.

## 1. 데이터와 정답지

| 항목 | 내용 |
|---|---|
| 입력 | 통합로그 12,313행 중 CloudTrail 10,223건, WAF 432건, PageSnap API 122건 |
| 제외 | 블루팀 CLI 조회 결과 1,536행. 공격자를 찾으려고 골라 조회한 결과라 넣으면 점수가 부풀려진다 |
| 가명 처리 | 공인 IP → 198.18.x.x, 계정 ID → 111122223333, 액세스 키 → 해시. 대응표는 저장소에 올리지 않는다 |
| 정답지 | 블루팀 보고서 2·3·5·6·7장에서 공격 9단계를 뽑아 **측정 전에 고정**했다 (`reports/ctf/gongbang_ground_truth.json`) |
| 공격자 | 보고서가 외부 사용 출처로 적은 IP 3개와 EC2 Portal 역할 키 1개 |

변환 과정에서 잃는 정보가 있다. 통합로그는 원본 JSON이 아니라 요약 표라서 WAF 요청의 쿼리·본문·헤더,
CloudTrail 요청 파라미터 대부분, 리전 정보가 없다. SSRF 주소(`169.254.169.254`)가 WAF 로그에 보이지 않는 것도 이 때문이다.

## 2. 공격 단계별 결과

| 단계 | 보고서 | 데이터에 있음 | 표시 | 잡은 규칙 | 묶인 사건 |
|---|---|---|---|---|---|
| G1 웹앱에 내부 주소 조회 요청(WAF 차단) | 3장 | 71건 | 71건 | WAF_BLOCKED | INC-002, INC-007 |
| G2 서명 없는 토큰으로 EKS 지원 API 접근 | 6장 | 29건 | 6건 | WAF_BLOCKED | INC-002 |
| G3 PageSnap 결과 PDF 내려받기 | 7장 | 10건 | **0건** | 없음 | 없음 |
| G4 EC2 역할 키를 외부 IP에서 사용 | 5장 | 13건 | 13건 | CT_INSTANCE_CRED_MULTI_IP | INC-002, INC-006 |
| G5 그 키로 워크플로 실행 성공 | 5장 | 9건 | 9건 | CT_INSTANCE_CRED_MULTI_IP | INC-002 |
| G6 그 키로 SSM 원격 명령·세션 시도(거부) | 5장 | 4건 | 4건 | CT_INSTANCE_CRED_MULTI_IP | INC-002, INC-006 |
| G7 신원·권한 정찰(15:17~15:25) | 2·5장 | **없음** | — | — | — |
| G8 Recovery 키 외부 사용, recovery.zip 전송 | 7장 | **없음** | — | — | — |
| G9 다른 키로 워크플로 실행(16:42) | 5장 | **없음** | — | — | — |

- G2는 29건 중 WAF가 차단한 6건만 표시했다. 허용된 23건은 요청 경로만 남아 있어 규칙으로는 정상 요청과 구별할 수 없다.
- G3을 놓친 이유: 같은 계정으로 PDF를 받는 것은 로그만으로는 정상 사용과 다르지 않다. 남의 작업 번호를 차례로 연 흔적(IDOR)이 있었다면
  웹 규칙(WEBLOG_IDOR_ENUM)이 잡을 수 있지만, 이 규칙은 아파치 로그 경로에만 연결돼 있고 API Gateway 로그에는 연결돼 있지 않다.
- G7~G9가 없는 이유: IAM·STS 호출은 다른 리전에, S3 객체 읽기는 데이터 이벤트로 남는데 통합로그의 event_history에는 둘 다 없다.
  event_history는 16:25:01에서 끝나 16:42 사건도 없다. 블루팀은 이 세 가지를 CLI로 따로 조회해 찾아냈다.

## 3. 사건 묶기 (공격 경로를 이었는가)

| 순위 | 사건 | 심각도 | 내용 | 공격자 이벤트 |
|---|---|---|---|---|
| 1 | INC-001 | 높음 | 블루팀의 조회 작업 + 블루팀의 CloudTrail·GuardDuty 설정 변경 | 0 / 432 |
| **2** | **INC-002** | 높음 | **WAF 차단(14:10~) → EC2 역할 키 외부 사용(15:36~16:08)** | **72 / 72** |
| 3 | INC-003 | 높음 | EKS 노드 역할 키가 AWS 안의 IP 두 곳에서 사용 | 0 / 13 |
| 4 | INC-004 | 높음 | 루트 계정 사용(운영측) | 0 / 153 |
| 5 | INC-005 | 높음 | GuardDuty 설정 변경(블루팀) | 0 / 2 |
| 6 | INC-006 | 높음 | 같은 키의 SSM 명령 시도(16:11). 사건 최대 길이 2시간을 넘어 INC-002에서 잘림 | 2 / 2 |
| 7 | INC-007 | 낮음 | 공격자의 두 번째 IP(같은 대역)에서 온 WAF 차단, 15:14~15:24 | 26 / 26 |

- 공격 사건 3개는 모두 공격자 이벤트만으로 이루어져 있다. 섞여 들어간 정상 이벤트는 없다.
- 하나의 공격이 3개 사건(INC-002·006·007)으로 나뉘었다. INC-006은 사건 최대 길이(2시간) 때문에 잘렸고,
  INC-007은 공격자의 다른 IP라 공유하는 키·주체가 없어 이어지지 않았다. 두 IP가 같은 /24 대역이라는 점은 규칙이 보지 않는다.

## 4. 오탐

공격자와 무관한데 표시된 이벤트는 600건이다(정밀도 14%).

| 원인 | 건수 | 판단 |
|---|---|---|
| 블루팀의 조회·설정 변경(CT_DISCOVERY_BURST 431, CT_LOGGING_TAMPER 3) | 434 | 행동 자체는 공격과 같다. 누가 블루팀인지 알려 주면 걸러진다 |
| 운영측 루트 계정 사용 | 149 | 루트 사용은 실제로 위험하므로 표시는 맞다. 공격은 아니다 |
| EKS 노드 역할이 AWS IP 두 곳에서 사용 | 13 | 진짜 오탐. 두 IP 모두 AWS 대역이다 |
| AWS 서비스 자체 호출 | 4 | 오탐 |

이벤트 단위 재현율(공격자 이벤트 566건 중 100건 표시, 18%)은 의미가 작다. 공격자 IP 이벤트 대부분이
웹앱 회원가입·화면 요청 같은 평범한 요청이라서다. 위의 단계별 결과를 기준으로 본다.

## 5. AI가 할 일 (다음 측정)

이 결과에서 규칙이 못 하는 일이 분명히 보인다. API 키를 받으면 아래를 같은 정답지로 잰다.

1. **오탐 재검토**: INC-001·003·004·005가 공격인지 판단. 블루팀 계정 이름, 두 IP가 모두 AWS 대역이라는 점 같은 맥락은 규칙보다 AI가 잘 본다.
   목표는 공격 사건을 1위로 올리는 것이다.
2. **공격 연결**: INC-002·006·007을 하나의 공격으로 합치고 순서(웹 → 키 → 실행 → 원격 명령 시도)를 설명.
3. **빈 곳 지적**: G7~G9처럼 로그가 없는 구간을 "이 로그로는 판단할 수 없음"이라고 말하는지 확인. 지어내면 감점.

ChatGPT 비교(조건 A)에는 같은 가명 처리 데이터를 쓴다. 통합로그 전체는 약 2MB라 한 번에 붙여넣을 수 없으므로,
비교 계획 문서의 절차대로 같은 구간을 잘라 세 조건에 똑같이 넣는다.

## 재현 방법

```
python scripts/ctf/convert_gongbang.py <통합로그.md> --out data/gongbang
python scripts/ctf/eval_gongbang.py --data data/gongbang --out reports/ctf/gongbang_rules_only.json
```

원본 로그와 가명 대응표(`data/`)는 저장소에 올리지 않는다.
