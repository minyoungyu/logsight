# 수집 보호 (방안 1+2): 공격자가 로그를 끊거나 지우지 못하게

수집을 "안 보이게" 숨기는 대신, **보여도 지울 수 없고, 끊으면 바로 알게** 만든다.
관리자 권한을 가진 공격자에게 이름 바꾸기 같은 위장은 거의 효과가 없다(역할 목록·신뢰 정책·CloudTrail에 그대로 보임).

## 구성

    감시 대상 계정                                   보관 계정(별도)                  분석 서버
    CloudTrail(모든 리전, 무결성 검증) ─────────→  S3 보관 버킷                 ←── logsight watch --s3 ... 읽기
    VPC Flow Logs ──────────────────────────────→  Object Lock(보관 기간 삭제 불가)
    웹서버 Fluent Bit(쓰기 전용) ── 1분 안에 ────→  hosts/<서버>/...
                                  └ 1분마다 ────→  heartbeat/<서버>/...        ←── --heartbeat: 5분 끊기면 경보
    (선택) SCP: 로그 끄기·지우기 금지

LogSight가 감시 대상 계정에서 로그를 "가져가는" 동작이 없다. AWS와 서버가 보관 계정으로 밀어 넣고, 분석 서버는
보관 계정에서 읽는다. 그래서 감시 대상 계정의 기록에는 LogSight의 읽기 흔적이 생기지 않는다.

## 방안 1: 계정 밖 보관

| 파일 | 어디에 | 하는 일 |
| --- | --- | --- |
| `deploy/aws/logsight-log-archive.yaml` | 보관 계정 | Object Lock 버킷(기본 GOVERNANCE 90일, 운영은 COMPLIANCE), 버전 관리, TLS만, 감시 대상 계정의 CloudTrail·Flow Logs 쓰기 허용, 서버 역할은 `hosts/`·`heartbeat/`에 쓰기만, LogSight는 읽기만 |
| `deploy/aws/logsight-source-logging.yaml` | 감시 대상 계정 | 트레일(모든 리전, 로그 파일 무결성 검증)과 VPC Flow Logs를 보관 버킷으로, 서버 역할용 쓰기 전용 정책 |
| `deploy/aws/scp-protect-logging.json` | AWS Organizations(선택) | 트레일 끄기·지우기, GuardDuty 끄기, Flow Logs 지우기, LogSight 경보 규칙 지우기를 `logsight-break-glass` 역할 말고는 금지 |

COMPLIANCE 모드는 보관 기간 안에 그 계정의 루트도 지울 수 없다. 시험할 때 COMPLIANCE로 만들면 기간 동안 비용을 못 줄이므로
처음에는 GOVERNANCE로 둔다.

Organizations를 쓰면 트레일을 조직 트레일로 만드는 것이 더 강하다. 회원 계정의 관리자는 조직 트레일을 끄거나 지울 수 없다
(관리 계정에서 `aws cloudtrail create-trail --is-organization-trail ...`). 이 저장소의 템플릿은 회원 계정 트레일을 만든다.

수정·삭제 확인: `aws cloudtrail validate-logs --trail-arn <트레일> --start-time <시각>`

## 방안 2: 서버 로그 즉시 전송과 끊김 경보

- `deploy/host/fluent-bit.conf`, `deploy/host/install.sh`: nginx 접속·auth·kern 로그를 원본 줄 그대로 1분 안에 `hosts/<서버>/`로 올린다.
  파일 이름에 nginx/auth/kern이 들어가 LogSight가 종류를 알아본다. 디스크 버퍼를 써서 네트워크가 잠시 끊겨도 나중에 보낸다.
- 1분마다 `heartbeat/<서버>/`에 생존 신호를 남긴다.
- `logsight watch --heartbeat s3://<보관 버킷>/heartbeat/`가 1분마다 확인해, 5분(`--heartbeat-max`) 넘게 신호가 없는 서버를
  높음 경보로 처리한다(분석·통지·자동 격리 흐름을 그대로 탄다). 따로 확인: `logsight heartbeat s3://<보관 버킷>/heartbeat/`

## 지켜 주는 것과 못 지키는 것

| 공격자 행동 | 결과 |
| --- | --- |
| 감시 대상 계정에서 이미 쌓인 CloudTrail·Flow Logs 지우기 | 불가(다른 계정 + Object Lock) |
| 서버를 장악하고 이미 보낸 nginx·auth 로그 지우기 | 불가(서버 권한은 쓰기만) |
| 트레일 끄기 | SCP가 있으면 불가. 없으면 가능하지만 StopLogging 경보로 바로 분석이 돈다 |
| 서버에서 Fluent Bit 끄기 | 가능. 5분 안에 끊김 경보 |
| 끄기 직전 1~5분 로그 | 잃을 수 있음(전송 주기·S3 전달 지연) |
| 가짜 로그 보내기(서버 root) | 막지 못함. 끊김 경보도 안 남. 진짜 로그와 섞인다 |
| 보관 계정 자체를 장악 | 이 설계 밖. 보관 계정은 사람 수를 최소로, MFA 필수 |

| 항목 | 상태 |
| --- | --- |
| 템플릿 3개 | cfn-lint 통과. **실제 계정에 올려 본 적 없음** |
| 생존 신호 확인(정상·10분 끊김·하루 넘게 없음)과 watch 경보 | moto(가짜 S3·SQS)로 시험 |
| Fluent Bit 설정 | **미시험**(실제 서버 필요). `install.sh`는 문법 검사만 |
| Object Lock 버킷에 CloudTrail·Flow Logs·Fluent Bit가 실제로 써지는지(Content-MD5 요구 등) | **미측정** |
| 비용 | **미측정**. S3 저장료와 요청료가 주 비용일 것으로 추정 |
