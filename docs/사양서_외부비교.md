# 비슷한 제품·오픈소스 사양과 비교해 더할 요구사항 (2026-11-20)

[사양서.md](사양서.md)의 요구사항을 비슷한 제품 7개의 공개 기능과 하나씩 대조했다. 목적은 "남들이 기본으로 갖춘 것 중
우리가 빠뜨린 것"을 찾는 것이다. 확인은 공식 문서·저장소의 검색 요약 기준이다(이 환경에서 일부 공식 페이지를 직접 열 수 없었다).
이전 비교([비슷한_제품_비교.md](비슷한_제품_비교.md))가 "무엇이 다른가"였다면 이 문서는 "무엇을 더해야 하나"다.

## 1. 대조 대상과 핵심 사양

| 제품 | 종류 | 사양에서 눈여겨본 것 |
|---|---|---|
| Amazon GuardDuty Extended Threat Detection | AWS 관리형 | 여러 데이터 원천·자원·시간에 걸친 다단계 공격을 '공격 순서(Attack sequence)' 결과 하나로 묶음. 모두 심각도 Critical. EC2·ECS·EKS·IAM·S3. 결과는 EventBridge로 나가고 S3로 내보냄. 보관(archive)·억제 규칙에 걸린 결과는 엮지 않음. 추가 비용 없음 |
| Amazon Detective | AWS 관리형 | CloudTrail·VPC Flow·GuardDuty·EKS 감사 로그로 행동 그래프. Investigation API가 IoC·TTP·범주형 심각도를 돌려줌. Security Hub의 결과도 읽음 |
| AWS Security Hub | AWS 관리형 | 새 버전은 결과를 OCSF 형식으로 모음(이전 CSPM은 ASFF). 자동화 규칙으로 심각도·상태·주석을 바꾸고, EventBridge로 Lambda·Step Functions·SSM 런북에 넘김 |
| Wazuh | 오픈소스 XDR/SIEM | 디코더+규칙(XML) 구조, 파일 무결성 감시(FIM), Active Response(SSH 대입 IP 차단·계정 잠금), 취약점·설정 점검, PCI DSS·HIPAA·GDPR 규정 대응표 |
| Sigma 규칙 + Suzaku(클라우드)·Chainsaw(Windows) | 오픈소스 | 공용 규칙 형식(Sigma)으로 CloudTrail 포렌식 타임라인, 사용자 ARN별 활동 요약. Chainsaw는 Windows 전용이라 CloudTrail 대상은 Suzaku |

| Matano | 오픈소스(AWS 보안 데이터 레이크) | Python 탐지가 들어오는 로그에 실시간으로 돎, Sigma 규칙 자동 가져오기, S3에 정규화해 저장 |

## 3. 판단 근거

1. **표준 형식 내보내기(OCSF/ASFF)는 보류.** Security Hub·Panther가 쓰는 형식이라 큰 회사 연동에는 쓸모가 있다. 우리 사용자(보안 담당 없는 작은 팀)는 Security Hub를 거의 쓰지 않고, 본선 심사 항목에도 직접 걸리지 않는다. 12/11 뒤 확장 과제로 둔다.
2. **파일 무결성 감시는 보류.** 웹 루트 웹셸 검사(FILE_WEBSHELL)는 있다. 상시 감시는 서버에 에이전트를 깔아야 하는데, "고객 서버에 아무것도 설치하지 않는다"는 설계와 부딪친다.
3. **Sigma 가져오기는 안 한다.** Suzaku가 Sigma 규칙 796개로 이미 잘한다. 같은 판에서 규칙 수로 겨루면 진다. 우리 규칙은 사건 묶기·판정과 엮여 있어 Sigma 하나를 그대로 넣으면 판정 품질이 오히려 흔들린다.
4. **규정 대응표는 안 한다.** 침해 '사고 대응' 도구라 규정 점검과 목적이 다르다. 설정 점검은 Prowler 같은 도구를 안내한다.
5. **sudo·su 권한 상승, 콘솔 로그인 대입, 인코딩 우회는 더했다.** 세 제품 이상이 기본으로 갖췄고, 우리 시연 시나리오(웹셸 → sudo find로 root)와 처음 보는 데이터 측정의 놓친 목록에 그대로 있던 것이다. 자세한 이유는 [코드프리즈_판단.md](코드프리즈_판단.md).
6. **자체 감사 로그는 다음 작업이다.** 사용자가 "이어서 할 일"로 이미 잡아 두었다(FR-21).
