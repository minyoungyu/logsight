# 비슷한 제품·오픈소스의 사양과 대조해 사양서에 더할 것 (v2, 2026-11-21)

[사양서.md](사양서.md)를 비슷한 제품 9개의 **공식 문서·저장소 원문**과 항목별로 대조했다. 목적은 두 가지다.
(1) 남들이 사양에 적어 두는데 우리 사양서에 빠진 항목을 찾는다. (2) 그중 **우리 목적에 맞는 것만** 받아들인다.

우리 목적(사양서 1절): 보안 담당자 없는 작은 팀이 경보 뒤 30분(늦어도 1시간) 안에 "공격인가, 어디가 뚫렸나, 무엇을 고치나"를 스스로 답한다.
그래서 받아들이는 기준은 하나다. **비전문가의 판단을 빠르고 정확하게 만드는가.** 탐지 개수를 늘리거나, 상시 운영자가 필요하거나,
고객 서버에 무언가를 설치해야 하는 기능은 아무리 흔해도 받지 않는다.

v1(11/20)은 검색 요약만 보고 썼다. v2는 원문을 읽었다. 읽은 방법과 못 읽은 것은 맨 아래 "확인 방법"에 적었다.

## 1. 대조 대상

| 제품 | 종류 | 우리와 겹치는 지점 | 원문 확인 |

| AWS Security Hub | AWS 관리형 결과 모음 | 자동화 규칙, OCSF | v1 검색 요약(이번에 다시 읽지 못함) |

| Suzaku | 오픈소스 클라우드 포렌식 타임라인 | CloudTrail 타임라인, 공격자 요약 | **README 원문** |
| Panther(panther-analysis) | 상용 SIEM의 공개 규칙 저장소 | 규칙 하나에 제목·심각도·런북·시험 데이터 | **규칙 원문**(aws_cloudtrail_rules) |
| Matano | 오픈소스 AWS 보안 데이터 레이크 | Python 탐지, 중복 제거 창, 임계값 | **README 원문** |

## 2. 사양 항목별 대조

○ 사양에 명시 · △ 일부 · × 없음 · — 해당 없음. 오른쪽 끝이 **판단**(우리 사양서에서 무엇을 했나).

### 2-1. 결과물(보고서·결과)에 무엇이 들어가나

| 항목 | 외부 제품의 사양 | LogFinder v2.0 | 판단 |
|---|---|---|---|
| 사건 묶기 | ETD: 여러 데이터 원천·자원·시간의 신호를 '공격 순서' 결과 하나로. Matano: 중복 제거 키 + 창(`deduplication_window_minutes: 15`) + 임계값(`threshold: 5`) | ○ FR-04(30분, 같은 IP·인스턴스·주체·키) | 같음. 유지 |
| 시간순 신호 | ETD: 결과에 Signals 탭(시간순), 신호마다 심각도. Suzaku: 관련 이벤트만 남긴 타임라인 | ○ FR-07 단계별 설명 | 같음 |
| 영향 받은 자원 | ETD: Overview에 신호·MITRE 전술·**영향 받은 자원**. Detective: TTP별 API 이름과 **성공·실패 수** | △ 자원은 흐름 그림에, "무엇에 닿았나"를 모은 칸 없음 | **더함: FR-25 피해 범위**(성공한 일과 닿은 자원을 한 칸에) |
| 민감 데이터 표시 | ETD 새 지표 SENSITIVE_DATA(Macie)·MISCONFIGURATION·REACHABILITY | × | **더함: FR-25 기준에** "사이트 프로필에 민감하다고 적은 버킷·경로면 표시". Macie 연동은 하지 않음(작은 팀은 안 켬) |
| 결과 제목 | Panther 규칙의 `title()`: "사용자 [이름]이 [함수 이름]의 설정을 바꿈"처럼 **누가·무엇을**이 제목에 들어감 | × 사건 제목이 첫 탐지 이름("GuardDuty: SSH 비밀번호 연속 실패") | **더함: FR-27**(가장 심각한 단계 + 주체·대상) |
| 조치 안내 | Panther: 규칙마다 `Runbook`(무엇을 확인하고, 아니면 키 비활성·세션 취소·되돌리기) + `Reference`. ETD: 권장 조치, "급한 것으로 다루고, 노출을 막고, 노출됐을 수 있는 자격증명·인스턴스 프로필을 교체" | ○ FR-08 수정·되돌리기 명령 쌍 | 같음. **순서 기준을 받아들임: FR-24**(번지는 것 막기 → 들어온 길 닫기 → 원인 고치기) |
| 심각도의 뜻 | Detective: 5단계(Critical~Informational), "심각도는 **그 자원의 행동**에 대한 판단이지 **자원이 조직에 얼마나 중요한지**가 아니다" | △ 심각도·확신도가 보고서에 있으나 사양서에 뜻이 없음(모의 시험 6명이 막힘) | **더함: 용어 절**에 심각도·확신도의 뜻, FR-28에 "확신도 뜻 한 줄" |
| 공격 기법 번호(ATT&CK) | ETD·Detective·Panther 모두 결과에 MITRE 전술·기법 | ○ FR-03 | 유지하되 **비전문가 화면에서는 접음**(FR-28). 전문가용 칸에는 그대로 |
| 표준 형식 내보내기 | Security Hub(OCSF), Matano(ECS 정규화) | ○ (2026-11-25) | `findings.ocsf.json`(OCSF 1.3.0 Detection Finding). 가져오기(Security Hub에 올리기)는 안 함 |

### 2-2. 정상 활동 빼기(억제)

| 항목 | 외부 제품의 사양 | LogFinder v2.0 | 판단 |
|---|---|---|---|
| 억제 방식 | GuardDuty: 필터 조건에 맞는 새 결과를 **자동 보관(archive)**, 보관된 결과는 90일 동안 볼 수 있음(늘릴 수 없음) | ○ FR-06 우리 팀 확인 | 같음 |
| 억제가 묶기를 약하게 함 | GuardDuty: **보관된 결과는 ETD 공격 순서의 신호로 쓰지 않음**, 넓은 억제 규칙은 다단계 탐지를 약하게 함 | △ 확인된 우리 팀이라도 "키 유출에서 흔한 모습이면 그래도 공격으로 봄"(보고서 문구). 뺀 이벤트를 묶기에 쓰는지는 사양에 없음 | **더함: FR-32 기준에** "판정에서 뺀 이벤트도 사건 묶기·흐름에는 쓴다" |
| 억제보다 분류 | SIR: 고정 억제 규칙 대신 분류(triage)를 선호, 오늘 정상이던 결과도 맥락이 바뀌면 다시 봄. 알려진 IP·IAM 주체로 기대 행동을 거름 | ○ 확인 전에는 판정을 바꾸지 않음 | 같음 |
| 뺀 것을 보여 주기 | GuardDuty: 보관된 결과를 상태 필터로 조회. CrowdSec: 허용 목록(AllowLists)을 명시적으로 관리 | △ 확인된 계정 이름만 보이고, **뺀 사건·이벤트 수와 목록은 안 보임** | **더함: FR-32**(뺀 활동을 보고서 끝에 수와 목록으로) |

### 2-3. 입력과 시점

| 항목 | 외부 제품의 사양 | LogFinder v2.0 | 판단 |
|---|---|---|---|
| 지난 로그 분석 | CrowdSec: 실시간과 **지난 로그(cold logs)** 모두, 지난 로그로 탐지 검증·포렌식·보고서 | ○ 경보 뒤 쌓인 로그 분석이 기본(U1) | 같음. 차별점: 도입 전 사고도 볼 수 있다 |
| 콘솔 이벤트 기록 CSV | Suzaku v3: CloudTrail **콘솔 '이벤트 기록' CSV**를 읽음. 단 "편하지만 정보가 빠지는 요약 형식", 796개 규칙 중 약 22개는 못 씀, 리전마다 따로 받아야 하고 전역 이벤트는 us-east-1, 영어 머리글만 | × FR-01의 9종에 없음 | **더함: FR-33(S)**. 트레일을 안 만든 작은 팀(U3 이전 단계)도 콘솔에서 90일 기록을 내려받아 바로 볼 수 있어 우리 사용자에게 맞다. 빠지는 정보를 보고서에 적는 것을 기준에 넣음 |
| 실시간 감시 | Wazuh·CrowdSec·ETD | × 경보 뒤 분석 | 안 함(v1과 같음, 위치가 다름) |
| 설치 | Wazuh: EC2에 에이전트 설치 또는 AWS 모듈. CrowdSec: 로그 처리기를 서버나 로그 파이프라인 옆에 설치. Matano: CLI로 서버리스 배포 | ○ 고객 서버 설치 없음(FR-17) | 차별점 유지 |

### 2-4. 자동 대응과 기록

| 항목 | 외부 제품의 사양 | LogFinder v2.0 | 판단 |
|---|---|---|---|
| 대응 종류 | Wazuh: 상태 없는 대응(한 번 실행, 되돌리지 않음, 예: 파일 삭제)과 **상태 있는 대응**(정해진 시간 동안 실행 뒤 **자동으로 되돌림**, 예: IP 임시 차단) | ○ FR-15 격리 4종, 삭제 없음, 되돌리기 명령 | 같음. 시간 제한 자동 해제는 받지 않음: 우리 격리는 키·사용자·역할 비활성이라 시간이 지나 저절로 풀리면 더 위험하다 |
| 대응 기록 | Wazuh: 대응마다 결과를 인덱스(이름·실행 파일·실행 위치)와 엔드포인트 로그 파일에 남김, 기본 보존 정책(롤오버 3일 뒤 삭제) | × FR-21 미구현 | **더함: FR-21 기준에** "격리를 실행했으면 무엇을, 누가 승인해, 언제 했는지" 한 줄 |
| 외부 통보 | SIR: EventBridge로 사건을 Jira·Slack·ServiceNow에. CrowdSec: 알림 플러그인 | ○ FR-14 | 같음 |
| 공동 차단 목록 | CrowdSec: 탐지한 공격을 공유하고 커뮤니티 차단 목록을 받음 | × | 안 함. 고객 로그를 밖으로 보내는 일이라 개인정보 약속(NFR-05·06)과 부딪친다 |

## 3. 사양서에 반영한 것 (v2.1)

| 반영 | 출처 제품 | 사양서 위치 |
|---|---|---|
| 피해 범위 칸: 성공한 일과 닿은 자원, 민감 자원 표시, 로그에 대상이 없으면 그렇다고 적기 | ETD(영향 받은 자원, SENSITIVE_DATA), Detective(API별 성공·실패) | FR-25 |
| 먼저 할 일의 순서: 번지는 것 막기 → 들어온 길 닫기 → 원인 고치기 | ETD 권장 조치 | FR-24 |
| 사건 제목에 가장 심각한 단계와 주체·대상 | Panther `title()` | FR-27 |
| 심각도·확신도의 뜻 | Detective | 용어 절, FR-28 |
| 뺀 활동을 보이게, 뺀 이벤트도 묶기에는 씀 | GuardDuty 억제·보관, SIR 분류 | FR-32 |
| 콘솔 이벤트 기록 CSV 입력(빠지는 정보 표시) | Suzaku | FR-33 |
| 격리 실행 기록 | Wazuh Active Response 기록 | FR-21 기준 |

받지 않은 것: 실시간 감시, 에이전트 설치(파일 무결성 감시 포함), Sigma 가져오기, 공동 차단 목록, 규정 대응표, 시간 제한 자동 해제.
이유는 모두 같다. 상시 운영자·설치가 필요하거나, 고객 로그를 밖으로 보내거나, 판단을 빠르게 하는 데 보탬이 없다.

## 4. 객관성에 대해

- 외부 제품이 "갖췄다"는 것은 **문서에 그렇게 적혀 있다**는 뜻이다. 실제로 써서 확인하지 않았다.
- 우리 쪽 ○는 사양서와 테스트 기준이다. 모의 사용자 시험([모의시험](사용자평가/모의시험_2026-11-21.md))에서 ○인 항목도 사람에게는 막혔던 곳이 있다(예: FR-12).
- 받아들인 항목이 우리에게 유리하게 고른 것으로 보이지 않도록, 받지 않은 항목과 이유를 같은 표에 남겼다.
