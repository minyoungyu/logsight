# LogFinder 제품 사양서 (v2.3, 2026-11-25)

제품 이름은 **LogFinder**(팀 이름)이고 명령어·패키지·폴더 이름은 `logsight`다. 이전 문서(중간보고 등)의 LogSight는 같은 제품이다.

v1은 지금 코드가 하는 일을 받아 적었다. v2는 **제품을 만든 목적에서 출발**해 성공 기준을 먼저 정하고, 요구사항과 우선순위를 그 아래에 두었다.
v2.2는 v2.1에서 새로 넣은 요구사항(FR-21·23~33, NFR-22~25)을 구현하고 상태를 자동 테스트로 바꿨으며, 제품 평가에 쓸 수 있는지 점검한 결과(11절)를 반영했다.
v2.1은 두 가지 점검 결과를 반영했다. (1) 보안 경험 없는 개발자 10명(가상)으로 돌린 [모의 사용자 시험](사용자평가/모의시험_2026-11-21.md)과 사양서 품질 점검(9절).
(2) 비슷한 제품 9개의 공식 문서·저장소 원문 대조([사양서_외부비교.md](사양서_외부비교.md)). 프리즈 판단은 [코드프리즈_판단.md](코드프리즈_판단.md).

요구사항 ID는 한 번 쓰면 다시 쓰지 않는다. 테스트 추적은 [테스트_체크리스트.md](테스트_체크리스트.md)와 `python scripts/spec_trace.py`로 확인한다.

## 0. 이 문서를 읽는 법

- **요구사항과 상태를 나눠 읽는다.** "요구사항"과 "받아들이는 기준" 칸이 목표다. "지금"과 "상태" 칸은 **2026-11-21 기준의 사실**이고 요구사항이 아니다.
- 상태: ✅ 기능이 있고 받아들이는 기준을 자동 테스트가 확인 · 🟡 목표는 넘었지만 표본·환경이 부족(개발 데이터만, 실계정 1회 등) · ⬜ 미구현이거나 목표 미달
- 우선순위: **M**(필수) U1을 끝까지 해내는 데 꼭 필요 · **S**(권장) 차별점과 신뢰 · **C**(선택) 운영 편의
- 낯선 말은 10절 용어에 있다.

## 1. 문제와 목적

LogFinder의 목적은 보안 담당자 없는 작은 팀이 경보를 받은 뒤 **30분 안에(늦어도 1시간 안에) "공격인가, 어디가 뚫렸나, 무엇을 고치나"를 스스로 답하게 하는 것**이다.
30분은 분석 15분과 보고서를 읽고 판단하는 15분을 더한 값이다(S4). 1시간은 넘으면 실패로 보는 상한이다.

- **문제.** CloudTrail, VPC Flow, WAF·ALB, 웹서버, auth.log가 다른 곳에 다른 형식으로 쌓여 하나씩 맞춰 봐야 한다. 공방전 블루팀에서 로그를 엮어 상황을 파악하는 데 막는 것보다 더 많은 시간이 들었다(신청서).
- **지금 도구로 안 되는 이유.** GuardDuty는 "이상하다"는 경보는 주지만 웹·서버 로그와 엮은 흐름, 원인 설정, 고칠 명령을 주지 않고 우리 팀 작업과 공격을 구별하지 않는다. 채팅 AI는 사용자가 무엇을 물을지 알아야 한다(기준선 실험: 공격 6단계 중 3단계, LogFinder 5단계). SIEM·Wazuh는 운영할 사람이 필요하다.
- **이겨야 하는 지점은 탐지 개수가 아니다.** (1) 판정이 맞다 (2) 비전문가가 이해한다 (3) 근거가 있고 안전하다.

## 2. 목표 사용자와 사용 상황

| 사용자 | 알고 있는 것 | 모르는 것 | 바라는 것 |
|---|---|---|---|
| 주: 백엔드 개발자(보안 담당 경험 없음) | EC2·S3·IAM 기본, nginx 로그 | ATT&CK, CloudTrail 읽는 법, 무엇이 정상인지, IMDS·NACL 같은 말 | 공격인가, 먼저 할 일 3가지, 복사해 쓸 명령 |
| 부: 팀장·대표 | 서비스 영향, 고객 대응 | 기술 세부 | 피해 범위, 유출 여부, 신고해야 하나, 보고서 한 장 |
| 부: 심사위원·멘토 | 보안 전문 지식 | 이 팀의 데이터 | 주장마다 측정 근거 |

- **U1 경보 뒤 분석**: 경보가 왔다. 로그를 올리거나 자동 분석을 받고, 30분 안에 판정과 먼저 할 일을 정한다.
- **U2 웹서버가 뚫렸나**: 웹·인증 로그와 웹 루트로 "시도만 했나, 이미 뚫렸나"를 안다.
- **U3 로그가 없는 팀의 준비**: 꺼진 로그를 찾아 켠다. 트레일이 없어도 콘솔의 90일 이벤트 기록으로 먼저 본다(FR-33).

사용 환경: 데스크톱 브라우저(1366×768 이상)가 기본이고, 경보를 휴대폰으로 받아 처음 여는 경우(390×844)도 있다(NFR-22).

## 6. 범위 밖, 가정, 위험

- **범위 밖**: 실시간 차단(IPS), 로그 장기 보관·검색(SIEM), 설정 자동 수정(격리 4종 제외), 규정 준수 점검, Sigma 가져오기, 서버 에이전트 설치(파일 무결성 상시 감시 포함), 공동 차단 목록 공유, **법률 판단**(FR-30은 확인하라는 안내까지만).
  요청 본문(POST)이 필요한 공격(XXE, 저장형 XSS, 가격 변조, 웹셸 내용)과 커널 취약점 권한 상승은 로그에 남지 않아 FR-09로 '모르는 것'에 적는다.
  다른 경로의 IDOR 성공은 사이트 프로필의 `private_object_paths`에 경로를 적어야 잡는다. 외부 제품과 비교해 받지 않은 것의 이유는 [사양서_외부비교.md](사양서_외부비교.md) 3절.
- **가정**: 사용자는 최소한 CloudTrail을 켜 두었거나 콘솔의 이벤트 기록을 내려받을 수 있다(아니면 U3이 먼저). 원본 로그 일부를 외부 AI에 보내는 것을 받아들인다(거부하면 규칙 모드, NFR-25).
  비전문가에게 가장 필요한 것은 판정과 먼저 할 일이다(모의 시험은 이를 지지하지만 증거가 아니다. S3로 확인한다).

## 7. 검증 계획과 지금 격차

- 회차마다 `python scripts/checklist_run.py`로 자동 TC 결과를 만들고, 수동 TC는 사람이 적는다. CI는 건너뛴 테스트를 실패로 본다.

- 모의 사용자 시험에서 드러난 약점(가상, 예측): 들어온 길(질문지 2번)과 탈취 계정(3번)을 보고서만으로 답하기 어렵다. 원인은 FR-23~28이었고 v2.2에서 구현했다. 고친 효과는 S3로만 확인한다.

## 9. 이 사양서는 실제 사양서로 쓸 수 있나 (품질 점검)

## 11. 제품 평가 기준으로 쓸 수 있나 (v2.2 점검)

심사위원(2절의 부 사용자)은 "주장마다 측정 근거"를 원한다. 이 문서를 그대로 제품 평가표로 쓸 때 문제가 될 수 있는 것을 하나씩 확인했다.

| 점검 | 결과 | 한 일 |
|---|---|---|
| 모든 ✅에 다시 돌릴 수 있는 확인이 있나 | ○ `python scripts/spec_trace.py`가 FR·NFR마다 TC가 있고 자동 TC 이름이 코드에 있는지 검사, `python scripts/checklist_run.py`가 결과를 만듦(11/21: TC 129개, 자동 107개 통과, 실패 0) | ⬜이던 23개를 자동 TC로 바꿈 |

| 개발 점수와 처음 본 데이터 점수를 나눴나 | ○ 3절 끝 원칙, S1·S5·S6·S7에 따로 적음 | S5·S6·S7에 개발 점수를 따로 적음 |
| 상태 기호를 정의대로 썼나 | △ FR-02가 일부 미구현인데 🟡였음 | ⬜로 |
| 문서끼리 숫자가 같은가 | △ README의 테스트 수(339)가 지난 숫자 | README를 고침. 코드프리즈_판단.md의 339는 그날 기록이라 그대로 둠 |
| 제품 이름이 하나인가 | ○ LogFinder(명령어 `logsight`) | FR-31 |
| 핵심 가치(비전문가 30분 판단)에 증거가 있나 | **× 없음.** S3·S4·NFR-16은 실제 사람 시험 0회. 모의 시험은 증거로 세지 않음 | 평가 때 이 점을 먼저 밝힌다. 시험 준비물과 진행 방법은 [설계](사용자평가/설계.md) |
