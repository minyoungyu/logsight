# LogSight 웹서버 침해 판단 — 설계와 검증

> "우리 웹서버, 이미 뚫렸나?"를 **서버에 이미 쌓여 있는 로그·파일만으로** 판단하고,
> 침입 흐름을 비전문가가 읽게 복원하는 도구. AWS 전용이던 LogSight를 리눅스 웹서버
> (nginx/Apache + PHP) 쪽으로 확장한 결과물이다.

## 왜 이 방향인가 (요약)

- 2025년 국내 침해사고 신고의 **44.2%가 서버 해킹**이고, 중소기업 홈페이지 웹 취약점·
  웹셸 공격과 연결된다. 침입부터 인지까지 **평균 106일**이 걸린다(SK쉴더스).
- 사고 뒤에 "지금 당장 쌓여 있는 로그로" 침해 여부와 흐름을 설명해 주는 **무료 도구는
  성숙한 게 없다**. 조각(CrowdSec=재탐지, ImunifyAV/휘슬=웹셸 파일, Wazuh=사전설치)은 있다.
- 그래서 LogSight의 정직한 위치는 "새 기능"이 아니라 **정답을 아는 공격으로 기존 무료
  도구와 비교해 무엇을 더 잡는지 숫자로 보여 주는 것**이다. 이 문서의 검증 harness가 그
  측정의 뼈대다. (차별화 논의 전체는 스레드 "LogSight 차별화 방향" 참고.)

## 구조

```
서버 로그/웹루트 (프로필로 지정)
  → web/weblog.py     접속·오류·인증 로그 파서 → 공통 Event 스키마(기존 코드 재사용)
  → web/webdetect.py  웹 공격 탐지 규칙(OWASP/MITRE ATT&CK 대응), 근거=원본 로그 줄
  → web/webscan.py    웹 루트 파일 점검(웹셸·백도어), 강한 신호 없으면 보고 안 함(오탐 억제)
  → correlate.py      공격자 IP·웹셸 경로로 이벤트를 '사건'으로 묶음(기존 코드 재사용)
  → web/webanalyze.py Claude 구조화 출력(침해 판정 verdict + 조치안) → 근거 검증(환각 거르기)
                      키 없으면 규칙 기반으로 같은 형식 생성
  → web/webreport.py  한 파일 HTML 보고서(판정 배너 + 공격 흐름 + 조치안 + 근거 로그)
  → web/webpipeline.py  assess(profile) — UI·CLI·테스트가 공통으로 쓰는 단 하나의 API
```

설계 원칙(기존과 동일): **원본 로그를 통째로 AI에 보내지 않는다. 모든 판단에 근거
위치(파일:줄)를 붙이고, AI가 댄 근거가 실제 입력에 있는지 코드로 다시 검사한다. 조치는
자동 적용하지 않는다.**

### 판정(verdict)

- `breached` 침해 확인 — 웹셸 파일 발견, 업로드 폴더의 스크립트 실행
- `likely_breached` 가능성 높음 — 공격 뒤 로그인 성공, 공격에 500 응답, 큰 응답 유출 의심 등
- `suspicious` 공격 시도는 있으나 성공 근거 불명확 — SQLi/traversal/스캐너 등 시도
- `no_evidence` 뚜렷한 근거 없음

### 미래 UI를 염두에 둔 API 계층

백엔드는 `assess(SiteProfile) -> dict`(UI가 그대로 그릴 JSON) 하나뿐이다. CLI
(`logsight scan`), 웹 화면(`/web`), JSON API(`/api/web/scan`), 테스트가 모두 이 함수를
부른다. 일반 사용자용 UI를 붙여도 백엔드를 다시 짤 필요가 없다.

## 실제 사이트에 쓰려면 (설정만 바꾸면 됨)

코드에 경로·IP를 박지 않았다. `profile.json` 하나만 바꾼다:

```json
{
  "name": "우리 사이트", "webroot": "/var/www/html",
  "log_paths": {
    "access": ["/var/log/nginx/access.log*"],
    "weberror": ["/var/log/nginx/error.log*"],
    "auth": ["/var/log/auth.log*"]
  },
  "login_paths": ["/wp-login.php"], "upload_dirs": ["/wp-content/uploads"],
  "trusted_ips": ["203.0.113.0/24"]
}
```

```
python -m logsight scan --profile profile.json --out reports/mysite
```

`.gz`·글롭(`access.log*`)·X-Forwarded-For(프록시 뒤 실제 IP)까지 처리한다.

## 검증 (lab/) — 정답을 아는 공격으로 측정

실제 사이트를 아직 컨택하지 못해, **로컬에 취약 웹사이트를 직접 만들고 직접 공격**해
정답(ground truth)이 있는 로그를 만들었다. 외부로는 아무 요청도 보내지 않는다.

- `lab/sites/shopmall`, `lab/sites/board` — 의도적으로 취약한 PHP 사이트 2종(검색 SQLi,
  로그인 무차별 대입, 경로 조작/LFI, 명령 삽입, 파일 업로드→웹셸). **경로 구조와 업로드
  폴더가 서로 달라** 프로필만으로 다른 사이트를 다루는 것을 보인다.
- `lab/serve.sh` — 실제 **nginx + php-fpm** 으로 띄운다(진짜 서버 로그가 쌓임).
- `lab/attack.py` — 정상 사용자 트래픽 + 유형별 공격을 서로 다른 (문서용)공인 IP로 보내고
  `ground_truth.json`에 "어떤 공격이 어떤 규칙으로 잡혀야 하는지"를 기록한다.
- `lab/evaluate.py` — 탐지 결과를 정답과 대조해 재현율·오탐을 센다.

```
bash lab/serve.sh start && python3 lab/attack.py && python3 lab/evaluate.py && bash lab/serve.sh stop
```

### 현재 결과 (2026-10-21, 규칙 기반)

| 측정 | 값 |
|---|---|
| 기대 규칙 재현율 | **17/17 = 100%** |
| 정상 트래픽 오탐 | **0건** |
| shopmall 판정 | 침해 확인 (사건 6, 탐지 14, 0.02초) |
| board 판정 | 침해 가능성 높음 (사건 4, 탐지 6, 0.01초) |

**이 숫자를 과장하지 않는다.** 공격과 탐지 규칙을 같은 사람이 만든 통제된 환경이라,
"현실 정확도"가 아니라 **파이프라인이 설계대로 동작하는지와 오탐 억제**를 보는 sanity
check다. 진짜 기여는 다음 단계다: **같은 정답 로그를 기존 무료 도구(CrowdSec 등)와 범용
LLM 붙여넣기에도 돌려 같은 표에 올려 비교**하는 것. `evaluate.py`는 그 비교를 끼워 넣을 수
있게 만들어 뒀다.

## 한계 (정직하게)

- 웹 접속 로그는 보통 **요청 본문(POST body)을 남기지 않는다.** 그래서 로그만으로 공격
  "성공"을 단정하기 어려운 경우가 있고, 도구도 그럴 때 `suspicious`로 남기고 unknowns에 적는다.
- 기본 로그 보관이 **14일**로 짧아, 인지가 늦으면 볼 로그가 없을 수 있다(보고서가 권고).
- `lab`의 SSH 탈취 시나리오 auth.log는 로컬에서 실제 SSH 무차별 대입을 돌리기 어려워
  **합성**했다(웹셸 시나리오와 같은 공격자 IP로 교차 상관만 확인). 웹 로그는 모두 실제다.
- 웹셸 파일 점검은 "확정"이 아니라 "사람이 볼 파일 추림"이다. 강한 신호가 없으면 보고하지
  않아 정상 앱 코드 오탐을 줄였지만, 완전하지는 않다.
