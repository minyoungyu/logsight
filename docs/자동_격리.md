# 자동 격리 (방안 A): 5분 안에 아무도 확인하지 않으면

경보가 높음인데 5분 동안 아무도 확인하지 않으면, **도입 이후 외부에서 만들어진** 키·사용자·역할·보안그룹 규칙만
되돌릴 수 있게 막는다. 지우지는 않는다. 기존 서비스 자원은 건드리지 않는다.
기본값은 **시험 모드**(`mode: dry-run`)라서 무엇을 했을지만 기록한다. 실제로 바꾸려면 설정을 `enforce`로 바꿔야 한다.

## 흐름

1. 경보가 오면 `logsight watch`가 분석하고, 같은 기간의 CloudTrail 생성 기록에서 격리 후보를 고른다.
   결과 폴더에 `response.json`(대기 중, 마감 시각)을 남기고 통지 요약에 "HH:MM까지 확인하지 않으면 N개 격리"를 넣는다.
2. 담당자가 확인하면 끝난다: `python -m logsight respond ack <결과 폴더>`
3. 마감이 지나면 `watch`가 20초 안에 처리한다(따로 돌릴 때는 `logsight respond tick`).
   실행 직전에 허용 목록을 다시 읽어, 그 사이 내부 생성으로 확인된 것은 빼고 한다.
4. 되돌리기: `python -m logsight respond undo <결과 폴더>` 또는 폴더의 `undo.sh`.

## 무엇을 막고 무엇을 안 건드리나

| 대상 | 조치 | 되돌리기 |
| --- | --- | --- |
| 기준선 뒤 만들어진 액세스 키 | 비활성(Inactive) | Active |
| 기준선 뒤 만들어진 IAM 사용자·역할 | AWSDenyAll 정책 부착(모든 호출 거부, 이미 받은 세션 포함) | 정책 떼기 |
| 기준선 뒤 열린 보안그룹 규칙 | 그 규칙만 닫기 | 같은 규칙 다시 열기(사람 권한으로) |

자동으로 하지 않는 것:

- 기준선(도입한 날 스냅샷)에 있는 사용자·역할·키·보안그룹 규칙
- 기존 사용자·역할의 권한 변경, 콘솔 비밀번호 생성(`AttachUserPolicy`, `CreateLoginProfile` 등). 막으면 서비스가 깨질 수 있어 "사람이 판단할 것"으로만 알린다
- AWS 서비스 연결 역할, 이름에 logsight가 들어간 역할
- 실패한 API 호출(만들어진 것이 없음)
- 삭제. 삭제는 보고서를 본 사람이 한다

## 내부에서 만든 것 구별(허용 목록 자동 갱신)

경보 연동 규칙이 `CreateAccessKey`·`CreateUser`·`CreateRole`·`AuthorizeSecurityGroupIngress`를 받을 때마다(등급과 무관)
만든 사람을 보고 허용 목록에 더한다.

- `deploy_principals`(CI/CD·Terraform 역할)가 만들었으면 허용
- `admin_principals`가 만들었으면 **관리 IP(`trusted_ips`)에서, MFA로** 만들었을 때만 허용

관리자 계정 하나만 보지 않는 이유: 공격자가 관리자 키를 훔쳐 새 키를 만들면 만든 사람은 "내부 사용자"로 찍힌다.
세 조건 중 하나라도 빠지면 후보로 남는다. 손으로 더할 때는 `logsight respond allow <종류> <ID>`.

## 안전장치

| 장치 | 설정 | 기본 |
| --- | --- | --- |
| 시험 모드 | `mode` | `dry-run`(기록만). 2주 동안 `would-do` 기록에 오판이 없으면 `enforce` |
| 확인 마감 | `deadline_min` | 5분 |
| 실행 등급 | `min_severity` | 높음만 |
| 사건당 한도 | `max_per_incident` | 5개(넘는 것은 `held`로 남기고 사람에게) |
| 하루 한도 | `max_per_day` | 20개 |
| 끄는 스위치 | `stop_file` 파일 또는 환경변수 `LOGSIGHT_RESPOND_STOP` | 있으면 모든 실행 중지(`stopped`로 기록) |
| 실행 권한 | `deploy/aws/logsight-responder.yaml` | 키 비활성, AWSDenyAll 붙이기·떼기, 보안그룹 규칙 닫기만. 삭제·생성·다른 정책 불가 |
| AI | 없음 | 대상과 조치는 규칙과 코드로만 정한다(로그 속 공격자 문자열이 판단을 조종하지 못하게) |

## 설치

1. 도입한 날 기준선을 뜬다(읽기 전용): `python -m logsight respond baseline --out baseline.json`
2. `deploy/respond.example.json`을 `respond.json`으로 복사해 배포 역할·관리자·관리 IP를 채운다.
3. 고객 계정에 실행 역할을 만든다: `deploy/aws/logsight-responder.yaml`(분석 서버 주체 ARN, ExternalId).
   `~/.aws/config`에 그 역할을 프로필로 넣는다.
4. `python -m logsight watch ... --respond respond.json --respond-profile logsight-responder`

## 측정한 것과 아닌 것

| 항목 | 상태 |
| --- | --- |
| 후보 고르기(탈취된 내부 키, 관리 IP·MFA 조건, 배포 역할, 기준선, 서비스 역할, 실패한 호출, 한도) | 단위 테스트 |
| 5분 전 대기, 확인하면 안 함, 끄는 스위치, 시험 모드 | 단위 테스트 |
| 키 비활성·거부 정책 부착·규칙 닫기와 되돌리기, 기준선 자원 그대로 | moto(가짜 AWS)로 시험. moto에 AWSDenyAll이 없어 같은 내용의 정책으로 대신함 |
| 저장소 샘플의 CreateUser | 실패한 호출(AccessDenied)이라 후보가 아님을 확인 |
| 실제 계정에서 실행, 실행 역할 템플릿 권한이 충분한지 | **미측정**(cfn-lint만 통과) |
| 오판률 | **미측정**(시험 모드 운영 기록이 있어야 함) |

알려진 한계: 공격자가 관리자 키를 계속 쥐고 있으면 격리한 키를 다시 켜거나 새로 만들 수 있다. 원래 훔친 내부 키는
기준선이라 자동으로 막지 않으므로 사람이 정해야 한다. 람다·EC2 키페어 같은 다른 지속성 수단은 아직 대상이 아니다.
