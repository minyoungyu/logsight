# 서브넷·VPC가 많은 환경 점검

2026-11-17에 합성 데이터로 재고, 2026-11-20에 고친 뒤 다시 쟀다. 실제 AWS 계정은 쓰지 않았다(moto와 합성 로그).
재현 스크립트는 `scripts/scale/`에, 회귀 테스트는 `tests/test_many_subnets.py`에 있다.

## 결론

서브넷이 1만 개여도 느려지거나 멈추지 않는다. 시간과 메모리는 서브넷 수가 아니라 로그 줄 수에 비례한다.
고치기 전에는 서브넷·VPC가 여러 개가 되면 수정안이 엉뚱한 곳을 가리켰고, 퍼블릭/프라이빗 서브넷을 구분하지 못했고,
서브넷을 넘는 공격(웹서버 침해 → DB)이 두 사건으로 끊겼다. 아래 표의 경우는 모두 고쳤다.

## 고치기 전과 후 (실제로 돌려 봄)

합성 환경: VPC당 서브넷 100개, 서브넷마다 서버 2대·보안그룹 1개·NACL 1개, 서버마다 사내 흐름 20건과 외부 443 접속 5건.
공격자 198.51.100.7이 서브넷 3의 서버 A와 서브넷 57의 서버 B를 스캔하고 22번에 접속한다. "전"은 main(2d4b395).

| 상황 | 서브넷 | 전 | 후 |
| --- | --- | --- | --- |
| 공격이 서브넷 두 곳에 걸침 | 1,000 | NACL 수정안 acl-00003 하나(B 빠짐) | acl-00003, acl-00057 둘 |
| VPC 10개가 모두 10.0.0.0/16, ENI 수집 | 1,000 | 다른 VPC의 서버 i-0090310·NACL acl-00903, 보안그룹 수정안 0개 | 맞는 서버·NACL 둘·보안그룹 둘 |
| 위와 같은데 ENI 정보 없음 | 1,000 | 위와 같음(틀린 서버) | 서버를 고르지 않고 "NACL 확인 필요"(실행 명령 없음), 가정에 안내 |
| 설정에 없는 대상(RDS·ALB 등)을 공격 | 5,000 | 보안그룹 수정안 1,002개, 첫 NACL, AI 입력 44만 자 | 묶은 수정안 1개(목록 1,002개는 resources), "NACL 확인 필요", AI 입력 7천 자 |

| VPC 대역 100.64.0.0/10, 배스천 SSH·모니터링 수집 | 1,000 | 사건 3개(자기 모니터링 서버를 "포트 스캔", 배스천을 "외부 관리 포트 접속"으로 잡고 NACL 차단 제안) | 사건 1개 |
| 퍼블릭 웹서버 침해 → 프라이빗 DB로 SSH 대입 → 웹서버 역할 키로 S3 대량 읽기 | 52 | 사건 2개, DB NACL에서 우리 웹서버 IP 차단 제안 | 사건 1개(출발지 2, 서버 i-web·i-db), 웹서버 격리 제안, "퍼블릭 서브넷의 i-web에서 프라이빗 서브넷의 i-db로" |

| 서브넷 | Flow 줄 수 | 전: 분석(초) / 메모리(MB) | 후: 분석(초) / 메모리(MB) |
| --- | --- | --- | --- |
| 1,000 | 50,030 | 0.39 / 95 | 0.33 / 97 |
| 5,000(스캐너·미확인 대상 포함) | 290,045 | 2.51 / 400 | 2.88 / 405 |

1만 개에서 2.3초 늘어난 것은 ENI·VPC로 서버를 고르는 단계다. 처음 구현은 23초였고, 같은 IP·VPC의 결과를 기억하게 하고
`mark_known`의 IP 대역 해석을 캐시해 7초로 줄였다.

## 무엇을 바꿨나

1. **수정안**(`config_audit.py`, `analyze.py`)
   - 사건 서버가 있는 모든 서브넷의 NACL에 수정안을 낸다. 서브넷을 모르고 NACL이 여럿이면 고르지 않는다(예전: 계정의 첫 NACL).
   - 대상 서버를 모르면 계정 전체 보안그룹에서 찾되, 그렇다고 적는다. 같은 종류 수정안이 5개를 넘으면 하나로 묶는다(명령은 앞 5개, 대상 전체는 `resources`).
   - 공격 출발지가 우리 서버면 그 서버를 침해된 서버로 보고 격리를 제안한다(디스크 스냅샷 → 격리 보안그룹 → 교체, 되돌리기 명령 포함). 그 IP는 NACL로 막지 않는다.
   - AI 입력의 수정안은 20개, IP·서버·주체 목록은 30개까지(전체 개수는 `*_total`).
2. **수집**(`aws_collect.py`, `aws_check.py`)
   - VPC 대역, 서브넷(라우팅 테이블에 인터넷 게이트웨이 경로가 있으면 `public: true`), 네트워크 인터페이스(ENI: EC2가 아닌 RDS·ALB·Lambda·NAT 포함, VPC·서브넷·보안그룹·IP), 인스턴스의 `vpc_id`.
   - NACL·VPC·보안그룹·Flow Logs는 페이지를 넘겨 모두 읽고, WAF 목록은 NextMarker로 넘긴다.
   - Flow Logs 점검이 VPC의 모든 서브넷에 서브넷 단위로 켠 것도 켜진 것으로 본다(예전: "없음"으로 보고 VPC 단위로 또 켬). 켤 때는 VPC를 25개씩 나눈다.
3. **서버 찾기**(`pipeline.enrich`)
   - VPC Flow의 interface-id(ENI)로 대상·출발지 서버를 먼저 찾고, 그다음 같은 VPC 안의 IP로 찾는다. 같은 IP가 여러 VPC에 있어 고를 수 없으면 `target_ambiguous`로 남기고 정하지 않는다.
   - 출발지가 우리 서버면 `src_instance`를 적는다.
   - nginx·Apache 로그는 어느 서버의 로그인지 적혀 있지 않으므로, 같은 IP의 Flow 기록이 우리 서버 한 대의 웹 포트로만 갔으면 그 서버를 대상으로 적는다(`target_inferred`). ALB·WAF 로그는 여러 서버 앞에 있어 하지 않는다.
4. **내부 확산 엮기**(`correlate.py`)
   - 우리 서버가 출발지인 의심 행동은 그 서버를 축으로 묶는다.
   - 서버 X에서 공격이 나가기 전 6시간 안에 X를 노린 심각도 높은 탐지가 있으면 두 흐름을 잇는다. 스캔만 한 IP(심각도 중간)는 잇지 않는다(테스트로 고정).
5. **사내 IP 판단**(`netaddr.py`)
   - 모듈마다 달랐던 기준(탐지는 10/172.16/192.168/127만, 정규화는 100.64·IPv6 포함, 그림·판정은 또 다름)을 하나로 합쳤다. RFC 1918, 100.64/10, 루프백, 링크 로컬, IPv6 ULA에 설정의 VPC·서브넷 대역(공인 대역을 쓰는 VPC 포함)을 더한다.

## 아직 안 되는 것

- 리전·계정이 여럿인 조직: 수집은 한 번에 리전 하나, 계정 하나다.
- 피어링·Transit Gateway·NAT 게이트웨이 경로: "이 서브넷에서 저 서브넷으로 갈 수 있나"를 판단하지 않는다. NAT 뒤 사설 IP가 공인 IP로 바뀌어 나가는 것도 잇지 못한다.
- 사설 출발지 VPC Flow의 내부 스캔 탐지는 main에 없다(PR #35에 있음). #35를 올리면 이 변경과 `detect.py`·`correlate.py`·`pipeline.py`에서 겹치므로 다시 맞춰야 한다.
- 실제 AWS에서 NACL·보안그룹 수천 개를 페이지 넘김으로 읽는 것은 moto로만 확인했다.
