# 클라우드 공방전 로그 AI 재검토 측정

측정일 2026-10-26 · 모델 claude-opus-5-5(모든 회차를 같은 모델이 응답) · 데이터와 정답지는 [규칙만 측정](공방전_로그_측정.md)과 같다.

## 한눈에 보기

- **판정 정확도 7/7, 공격 사건 순위 2위 → 1위.** 변경 전후 모두 같고, 3회 반복해도 같았다. 블루팀 조회(INC-001)는 정상 활동으로, 루트 사용(INC-004)은 '공격 아님·위험 설정'으로 내려갔다.
- **공격 사건 3개를 하나로 묶었다(3회 모두).** 변경 전에는 INC-007이 따로 남았다. 가명 처리가 IP를 하나씩 번호 매기면서 두 공격자 IP가 같은 /24라는 정보를 지웠기 때문이다. 대역을 남기도록 바꾸자 AI가 '같은 대역, 같은 경로, 같은 초에 함께 차단'을 근거로 이었다. 가명 처리만 바꾼 1회 실행에서도 이미 묶였다.
- **IDOR 탐색을 클라우드 분석에서도 잡는다.** 새 규칙 WEB_OBJECT_ENUM이 PageSnap API에서 남의 작업 번호(job-0, job-1, job-5000 등)에 403/404를 연달아 받은 16건을 표시했다. 모두 공격자 IP였고 정상 이벤트 오탐은 늘지 않았다(600건 그대로).
- **로그에 없는 단계를 '모름'이라고 말한다.** S3 객체 읽기(G8)는 3회 모두 'S3 객체 호출이 0건이라 읽기·반출이 있었어도 이 로그에는 남지 않는다'고 적었다. 로그가 끝난 뒤(G9)도 3회 모두 언급했다. 탈취 키의 정찰(G7)이 사용 내역에 없다는 지적은 3회 중 1회만 나왔다.
- **근거 검증 통과.** 근거 ref 155개 중 입력에 없는 것 0개, 없는 사건 ID 0개.

## 2. 무엇을 바꿨나

1. **가명 처리(`scripts/ctf/convert_gongbang.py`)**: 같은 실제 /24에 있던 IP는 가명도 같은 /24에 둔다. 실제 대역·호스트 번호는 드러나지 않는다(나온 순서대로 번호). 정답지의 공격자 IP 3개는 같은 실제 IP의 새 가명으로 기계적으로 옮겼다(198.18.7.1, 198.18.7.2, 198.18.50.1). 공격자 집합과 단계는 그대로다.
2. **IDOR 탐색 규칙(`WEB_OBJECT_ENUM`, `logsight/detect.py`)**: ALB·API Gateway 로그에서 같은 IP가 같은 API(경로의 숫자 조각을 {id}로 바꾼 모양)의 서로 다른 객체 5개 이상에 10분 안에 403/404를 받으면 표시한다. 웹서버용 WEBLOG_IDOR_ENUM은 `/order.php` 이름에 묶여 있어 그대로 연결할 수 없어 새로 만들었다. 확장자가 있는 정적 파일 404는 세지 않는다.
3. **로그 범위 요약(`coverage`, `logsight/triage.py`)**: AI 재검토에 로그 종류별 기간, 빠진 로그 종류(vpcflow·sshauth), CloudTrail S3 객체 호출 수(0), 자격증명 규칙에 걸린 키의 전체 호출 내역을 함께 보낸다. 프롬프트에 '정찰, 데이터 읽기·반출처럼 있을 법한 단계가 로그에 없으면 없었다고 단정하지 말고 왜 안 보이는지 적으라'는 문장을 넣었다.

## 3. 주의할 점

- **이 결과는 독립 측정이 아니다.** 세 가지 변경 모두 이 데이터에서 본 약점을 보고 만들었다. 규칙과 프롬프트는 일반 원칙으로 썼지만(특정 IP·경로·시간을 넣지 않음), 성능 주장에는 AIT 같은 다른 데이터의 측정을 함께 써야 한다.
- G7·G8은 '탐지'가 아니라 '로그에 없다고 말함'이다. 입력에 흔적이 없으니 잡을 수 없다. 실제로 잡으려면 CloudTrail S3 데이터 이벤트와 전 리전 수집이 필요하다.
- G3(PDF 내려받기, 성공 응답)은 여전히 0건이다. 새 규칙은 403/404만 보므로, 공격자가 탐색 직후 남의 작업 번호에서 200을 받은 기록(14:45~14:46)은 표시하지 않는다. AI도 'IDOR 중 성공한 접근이 있었는지 입력에 없다'고 했는데, 원본 로그에는 있다. 다음 개선 후보는 'IDOR 탐색 IP가 같은 API에서 받은 성공 응답'을 사건에 함께 넣는 것이다.
- 7.1과 7.2를 같은 공격자로 본 것은 대역·경로·시간에 기댄 추정이다. 3회차는 이를 '추정'이라고 스스로 적었다.

## 5. 공격 흐름 설명 (변경 후 1회차)

**INC-007 + INC-002 + INC-006**: 198.18.7.x의 공격자가 웹 앱(pagesnap, /api/subscriptions, /api/cases)을 탐색·공격했다. 이후 portal 인스턴스 역할 키 ASIA71C2…95CF를 손에 넣어 Step Functions 실행에 성공했고, SSM 명령 실행은 권한 부족으로 실패했다.

- 묶은 이유: 198.18.7.1과 198.18.7.2는 같은 대역이고 같은 경로(POST /api/subscriptions, GET /api/cases/…)를 노렸다. 06:24:09에는 두 IP가 같은 초에 WAF에 막혔다. 탈취된 키 ASIA71C2…95CF는 198.18.50.1과 공격 IP 198.18.7.1 양쪽에서 쓰였다.
- 2026-10-11T05:10:45+00:00 (INC-002) 198.18.7.1의 POST /api/subscriptions 공격 요청이 WAF에 막히기 시작함
- 2026-10-11T05:40:24+00:00 (INC-007) 198.18.7.2가 jobs 객체 번호를 바꿔 가며 IDOR 탐색, 모두 실패
- 2026-10-11T06:15:36+00:00 (INC-007) 198.18.7.2도 /api/subscriptions, /api/cases 요청이 WAF에 막힘
- 2026-10-11T06:24:09+00:00 (INC-002) 같은 시각 198.18.7.1의 /api/cases, /api/support/incidents 요청이 막힘
- 2026-10-11T06:52:08+00:00 (INC-002) portal 역할 키가 정상 IP가 아닌 198.18.50.1에서 states:StartExecution 성공(키 첫 사용은 06:36:22)
- 2026-10-11T07:11:37+00:00 (INC-006) 같은 키로 198.18.7.1에서 ssm:SendCommand 시도, AccessDenied로 실패

## 6. '판단할 수 없음' 항목 (변경 후 1회차)

- portal 역할 키 ASIA71C2…95CF가 어떻게 유출됐는지 알 수 없다. 키 첫 사용(06:36:22)은 ALB 로그(06:27:00까지)와 WAF 로그(06:32:26까지)가 끝난 뒤라 그 사이 웹 요청이 보이지 않는다. 입력 events에는 WAF가 막은 요청만 있어서, 통과한 요청이 성공했는지도 모른다.
- 198.18.50.1이 공격자 IP인지, 인스턴스의 다른 정상 출구인지 입력만으로 확정할 수 없다.
- states:StartExecution 9건이 어떤 상태 머신을 어떤 입력으로 실행했는지, 실행 결과가 무엇이었는지 알 수 없다.
- ssm:StartSession 실패 2건은 events에 없어 어느 IP에서 언제 시도했는지 알 수 없다.
- CloudTrail S3 객체 단위 호출이 0건이라 S3 데이터를 읽거나 가져갔는지 보이지 않는다. VPC Flow Logs도 없어 네트워크로 데이터를 반출했는지 확인할 수 없다.
- IDOR 탐색에서 성공한 다운로드가 있었는지는 입력 events(실패만 있음)로 알 수 없다.
- 탈취 키로 한 정찰 호출은 이 키의 사용 내역에 없다. 공격자가 다른 경로나 자격증명으로 정찰했는지는 알 수 없다.
- CloudTrail 로그가 07:25:01에 끝나 그 뒤 공격자 행동은 알 수 없다.
- INC-001의 감사 로그 중지·삭제 1건과 INC-005 GuardDuty UpdateDetector의 구체적 변경 내용은 입력에 없다.
- 루트 계정이 누구의 세션인지, 왜 여러 IP에서 쓰였는지 알 수 없다.

## 재현

```
python scripts/ctf/convert_gongbang.py <통합로그.md> --out data/gongbang
python scripts/ctf/eval_gongbang.py --data data/gongbang --out reports/ctf/gongbang_rules_only.json
python scripts/ctf/eval_gongbang.py --data data/gongbang --ai --out reports/ctf/gongbang_ai.json
```

변경 후 1회차 결과 전체는 `reports/ctf/gongbang_ai.json`이다. G7~G9 지적 여부는 사람이 cannot_tell을 읽고 셌다.
