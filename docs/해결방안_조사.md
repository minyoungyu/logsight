## 1. 정확도를 숫자로 증명하기

| 방안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. **Stratus Red Team** (Datadog 오픈소스) | AWS 공격 기법을 정해진 방식으로 실행·정리해 주는 도구. 기법별로 언제 무엇을 했는지 알 수 있어 정답지로 쓰기 좋다 | 기법이 ATT&CK과 연결돼 있고, 탐지 규칙 검증용으로 만들어졌다 | 실습용 AWS 계정이 필요하다(팀 계정, 운영 계정과 분리) |
| B. CloudGoat (Rhino Security Labs) | 일부러 취약하게 만든 AWS 실습 환경 | 공격 "순서" 전체를 재현할 수 있다 | 정답지를 직접 만들어야 한다 |
| C. 공개 데이터셋(flaws.cloud 등) | 이미 처리함 | 비용 0, 규모 큼 | 정답이 없어 정밀도·재현율을 못 구한다 |
| D. 직접 만든 합성 로그 | 지금 samples처럼 | 빠르다 | 우리가 만든 것을 우리가 잡는 셈이라 설득력이 약하다 |

**추천: A + C 조합.** A로 기법 5~10개를 실습 계정에서 실행해 "어떤 기법을 몇 개 맞혔나(재현율)"를 재고, C(flaws.cloud)에서 "사건 중 실제로 의미 있는 비율(정밀도)"을 사람이 표본 50건으로 채점한다.
측정 항목은 단계 판별 정확도, 근거 로그 정확도(이미 자동 검증 중), 분석 시간이다.

## 2. Claude 분석 품질 확인과 AI 비용

- 현재 기본 모델 `claude-haiku-5-5`의 공개 단가는 입력 100만 토큰당 0.10달러, 출력 0.50달러다(프롬프트 10만 토큰 이하 기준).
- 데모 사건 하나를 AI에 보내는 입력은 약 7KB(측정)라서 입력 약 3천 토큰, 출력은 약 1,500토큰으로 잡았다(추정).
  그러면 **사건당 약 0.001달러(0.1센트)** 다. 상위 10건 분석은 1센트 정도다.
  Haiku 5.5는 생각(thinking)이 기본으로 켜져 있고 생각 토큰도 출력으로 계산되므로 실제로는 몇 배 늘 수 있다. 첫 실행 때 `usage`로 실측한다.
- 비교용 `claude-sonnet-5-5`는 입력 2달러, 출력 10달러라 같은 사건이 약 2센트다.
- 비용을 더 줄이는 방법(Anthropic 공식 문서):
  - **Batch API**: 모든 사용량이 표준 가격의 50%. 24시간 안에 처리(대부분 1시간 이내). 밤사이 일괄 분석에 맞다.
  - **프롬프트 캐싱**: 매번 같은 시스템 프롬프트·스키마를 캐시. 배치와 할인이 겹쳐 적용된다.
- 품질 확인 방법: 사건 10개에 대해 Haiku와 Sonnet 결과를 같이 만들고, 팀원 2명이 "단계가 맞나, 근거가 맞나, 수정안을 그대로 따라 할 수 있나"를 1~5점으로 채점한다.

**결론: AI 비용은 걸림돌이 아니다.** 판매 가격을 정할 때 원가에서 거의 빼도 될 수준이다(추정).

## 3. 경보 수 줄이기 (flaws.cloud 사건 1,871건)

| 방안 | 내용 | 예상 효과 |
| --- | --- | --- |
| A. **위험 점수 재설계** | 지금 점수는 심각도·규칙 수·이벤트 수만 본다. 단계 수(정찰→권한 상승→유출처럼 여러 단계), 성공 여부, 새 IP 여부를 넣는다 | 화면 상위 10건의 질이 오름. 총 건수는 그대로 |
| B. **같은 패턴 묶기** | "같은 IP가 매일 같은 정찰"처럼 반복되는 사건을 하나로 접고 "N일간 반복"으로 표시 | flaws.cloud처럼 같은 공격자가 반복하는 데이터에서 크게 줄 것(추정) |
| C. **알려진 정상 목록** | 고객이 "이 IP·이 역할은 정상"이라고 표시하면 다음부터 제외. CI/CD 역할, 모니터링 도구 등 | 오탐이 고객별로 줄어듦 |
| D. 기준선(평소 행동) 학습 | 계정별로 평소 쓰는 API·리전·시간대를 학습해 벗어난 것만 경보 | 효과는 크지만 데이터가 쌓여야 하고 구현이 복잡 |
| E. GuardDuty에 맡기기 | 탐지는 GuardDuty, LogSight는 설명만 | 건수 문제를 AWS로 넘김 |

**추천: A → B → C 순서.** D는 3단계. 성공 기준은 "flaws.cloud에서 화면에 보여 줄 사건 상위 10건 중 사람이 보기에 의미 있는 것 8건 이상".

## 4. GuardDuty와 겹치는 문제

- GuardDuty는 결과를 EventBridge로 보내거나 S3로 내보낼 수 있다. S3 내보내기는 새 결과를 약 5분 안에 `.jsonl.gz`로 쓰고, KMS 암호화가 필수다.
- 방안:
  - A. **GuardDuty 결과 파서 추가**: S3로 내보낸 JSON Lines나 `get-findings` 결과를 그대로 읽어 사건으로 만들고, 같은 IP·인스턴스·키로 우리 로그와 엮는다. 수정안 엔진(config_audit)은 그대로 쓴다.
  - B. Security Hub(ASFF/OCSF) 결과까지 받기: Prowler 같은 다른 도구 결과도 한 번에 들어온다.
  - C. 경쟁하지 않고 무시: 심사에서 차별점 질문에 약하다.
- **추천: A를 2단계에 구현, B는 형식만 맞춰 둔다.** "GuardDuty가 '이 인스턴스 자격증명이 밖에서 쓰였다'고 하면, LogSight는 '어느 보안그룹·IAM 정책 때문에 가능했고, 이 명령으로 고친다'까지 한국어로 말해 준다"가 판매 문구가 된다.

## 5. 로그·설정을 맡기기 불안한 문제

| 방안 | 내용 |
| --- | --- |
| A. **로컬 실행 기본** | 지금도 CLI로 고객 PC나 서버에서 돈다. 웹은 데모용으로만 쓴다고 명시 |
| B. **AI 전송 전 미리 보기** | `--dry-run`으로 Claude에 보낼 JSON(마스킹 후)을 파일로 저장해 먼저 보여 주기. 지금도 원문 전체가 아니라 축약·마스킹된 사건만 보낸다 |
| C. **AI 없이도 쓸모 있게** | `--no-ai` 규칙 기반 보고서가 이미 있다. 민감한 고객은 AI를 끄고 쓸 수 있다 |
| D. **고객 계정의 Amazon Bedrock으로 Claude 호출** | Bedrock 문서에 따르면 요청·응답이 모델 제공자에게 전달되지 않고, 보관 여부도 설정할 수 있다(일부 최신 모델은 AWS 내부 검토용 최대 30일 보관). 고객 데이터가 고객 AWS 계정 밖으로 안 나간다는 설명이 가능하다 |
| E. 국내 규제 대응 | 로그에 개인정보(IP, 사용자 이름)가 있으면 국외 처리 고지가 필요할 수 있다. 마스킹 범위를 IP까지 넓히는 옵션 |

**추천: A·B·C는 바로(작업량 작음), D는 2단계 선택 기능.** Bedrock은 Anthropic SDK의 Bedrock 전용 클라이언트로 같은 코드 구조를 유지할 수 있다.
E는 법률 검토가 필요하므로 보고서에는 "검토 예정"으로만 적는다.

## 6. "결국 사람이 고쳐야 한다"

| 방안 | 내용 |
| --- | --- |
| A. **되돌리기 명령 같이 주기** | 보안그룹 규칙 제거 → 다시 추가하는 명령을 같이 출력. 겁내지 않고 적용하게 |
| B. **영향 범위 표시** | "이 보안그룹을 쓰는 인스턴스 3대", "이 역할을 쓰는 서비스" 같은 정보를 설정 수집 결과로 계산 |
| C. **단계적 적용** | WAF는 COUNT로 먼저, 보안그룹은 관리자 IP 허용을 먼저 추가하고 0.0.0.0/0 제거 |
| D. 자동 적용 | 이번에 로그 켜기(`--apply`)는 명시적 동의 하에 넣었다. 방화벽 변경 자동 적용은 서비스 중단 위험이 있어 계속 하지 않는다 |
| E. IaC 출력 | Terraform/CloudFormation 조각으로 수정안을 출력해 코드 리뷰를 거치게 |

**추천: A·B·C.** 로그 켜기처럼 서비스에 영향이 없는 것만 자동 적용하고, 방화벽은 사람이 적용한다는 원칙을 유지한다.

## 7. 실시간 분석

- A. S3에 로그가 쌓일 때마다 Lambda로 LogSight를 돌리고 high 사건만 알림(Slack/메일).
- B. 하루 한 번 일괄 분석(cron, GitHub Actions 예약 실행). Batch API와 잘 맞고 가장 쉽다.
- C. EventBridge 규칙으로 위험한 API(StopLogging, CreateAccessKey 등)만 즉시 알림. LogSight 없이도 되는 무료에 가까운 방법이라 `check` 결과에서 안내하는 게 맞다.
- **추천: 2단계는 B + C 안내, A는 3단계.**

## 8. 메모리(194만 건에 2.7GB)

- A. `--since/--until` 시간 범위 필터: 사고 시점 앞뒤만 읽기. 가장 효과가 크고 쉽다.
- B. 파일 단위 스트리밍: 탐지에 필요한 집계만 남기고 이벤트 본문은 버리기. 사건 근거는 파일 위치(raw_ref)로 다시 읽기.
- C. DuckDB/Parquet로 변환해 질의: 대용량은 좋지만 의존성이 늘어난다.
- **추천: A 먼저, B는 이후.**

## 9. 사업 모델과 AWS 밖 확장

- 이번에 만든 무료 대안 로그(서버 방화벽, nginx/apache)는 **클라우드 종류와 상관없이** 리눅스 서버면 된다. NCP, 가비아, 카페24 서버 호스팅에도 그대로 쓸 수 있다(안 살 이유 9에 대한 부분 답).
- 단계별 시장(추정):
  1. 대학 수업·동아리·공방전: 무료. 사용 실적과 정확도 데이터를 모은다.
  2. 보안 담당자 없는 소규모 기업: `check` + 월간 보고서 구독. AI 원가가 사건당 0.1센트 수준이라 저가 구독이 가능하다.
  3. 보안 관제 업체(MSSP): 한국어 설명 엔진을 API로 제공.
