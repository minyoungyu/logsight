# 사내 IP 공격자 엮기 측정 (2026-11-13)

## 무엇을 고쳤나

공격자가 사내(사설) IP면 사건이 요청마다 흩어졌다. 원인은 두 가지였다.

1. nginx·Apache 접속 로그(`weblog`)의 사설 IP는 연결고리가 아니었다. 그래서 경로 대입 404가 한 건씩 따로 사건이 됐다.
2. VPC Flow·서버 방화벽의 사설 출발지는 탐지에서도 엮기에서도 빠졌다. 같은 공격자의 포트 스캔이 웹 공격과 이어지지 않았다.

사내 IP를 아무 조건 없이 연결고리로 쓰면 다른 문제가 생긴다. 로드밸런서 뒤 웹서버에 X-Forwarded-For가 없으면 모든 사용자가 로드밸런서 주소 하나로 보이고, 서로 무관한 사용자의 의심 행동이 거대한 사건 하나로 뭉친다. 사내 서버끼리의 통신(10.x ↔ 10.x)을 모두 이으면 무관한 활동이 다 이어진다. 그래서 아래 기준을 같이 넣었다.

## 기준

| 로그 | 사설 IP를 연결고리로 쓰나 | 코드 |
| --- | --- | --- |
| 웹·엣지·인증(nginx·Apache, ALB, WAF, SSH) | 쓴다. 단 **공유 주소**는 뺀다 | `correlate._key_policy` |
| 네트워크(VPC Flow, 서버 방화벽) | 웹·서버 로그에서 **의심 행동이 잡힌 IP만** 쓴다 | `detect.anchored_private_ips` |
| 그 밖(CloudTrail의 VPC 엔드포인트 주소 등) | 쓰지 않는다(전과 같음) | |

**공유 주소**(`detect.shared_private_ips`)는 여러 사용자가 함께 쓰는 사설 IP다. 다음 중 하나면 공유 주소로 본다.
- 상태 확인 요청을 보낸다(User-Agent에 `ELB-HealthChecker`, `kube-probe`, `HealthCheck` 등). 로드밸런서·프록시 주소다.
- 다른 요청의 X-Forwarded-For 앞 단계(프록시)로 보인 적이 있다.
- User-Agent가 20종 이상이다. AIT의 사내 NAT 주소(공격자와 원격 근무자가 함께 씀)는 4일 동안 7종이었다. 인터넷 사용자를 받는 로드밸런서는 수십~수백 종이 된다.
- 설정 `environment.json`의 `shared_ips`(CIDR 목록)에 있다. 자동 판단이 안 되는 주소를 사람이 적는다.

공유 주소로 본 IP는 보고서의 "가정" 칸에 이유와 함께 적는다.

**의심 행동이 잡힌 사내 IP**의 VPC Flow·서버 방화벽 기록은 포트 스캔·관리 포트 접속 규칙을 공인 IP와 같은 기준으로 다시 본다. 단 그 의심 행동의 앞뒤 6시간 안의 기록만 본다(`detect.ANCHOR_SPAN`). 정찰은 침투보다 먼저 오므로 앞쪽을 넉넉히 두되, 같은 주소의 며칠 전·후 정상 통신까지는 보지 않는다. 의심 행동이 없는 사내 IP의 네트워크 기록은 전처럼 탐지하지 않고, 사건 맥락에도 붙지 않는다.

### 로드밸런서 뒤 웹서버(합성)

- 공유 주소 판단을 끄면 두 공격자가 한 사건으로 뭉친다(테스트 실패로 확인).
- 켜면 뭉치지 않고, 보고서 가정 칸에 "사내 IP 10.20.0.5는 여러 사용자가 함께 쓰는 주소로 보여 연결고리에서 뺐습니다"가 나온다.

## 한계

- **공유 주소인데 판단 신호가 없는 경우**: 사용자 몇 명뿐인 사내 앱이 X-Forwarded-For 없는 프록시 뒤에 있고 상태 확인 요청도 없으면 공유 주소로 보지 못한다. 이때 그 사용자들의 의심 행동은 한 사건으로 묶일 수 있다. `shared_ips`에 적으면 막힌다.
- **공유 주소에서 온 공격은 다시 흩어진다**: 공유 주소로 본 IP의 의심 요청은 연결고리가 없어 건마다 사건이 된다(반복 사건 접기에서 하나로 보인다). 실제 사용자 IP를 알려면 로그에 X-Forwarded-For를 남겨야 한다.
- **User-Agent를 계속 바꾸는 공격자**: 한 사설 IP에서 20종 이상을 쓰면 공유 주소로 보아 엮이지 않는다. 흔한 도구(sqlmap·wpscan의 `--random-agent`)는 실행마다 한 종을 고르므로 보통은 넘지 않는다 **(추정, 측정 안 함)**.
- **VPC Flow는 변환본**이다. 실제 사내 VPC Flow(사내 서버끼리의 대량 통신)로 "의심 행동이 없는 사내 IP는 엮이지 않는다"를 측정하지는 않았다. 코드상 그런 IP는 연결고리가 되지 않는다(단위 테스트로 확인).
- 사설 IP 판단은 탐지 쪽 기준(`detect._is_private`: 10/8, 172.16/12, 192.168/16, 127/8)을 쓴다. 100.64/10(CGNAT)·169.254/16은 전처럼 공인으로 취급된다.

## 재현

AIT 파일은 `scripts/public/fetch_ait.py`의 `RangeFile`로 필요한 항목만 받았다(zip 전체를 받지 않음). VPC Flow 변환과 항목 받기에 쓴 스크립트는 프로젝트 노트의 `정규화_검증/ait_get.py`, `ait_eve2vpc.py`다. 개선 전은 `main`을 `git worktree`로 따로 꺼내 같은 명령으로 돌렸다.
