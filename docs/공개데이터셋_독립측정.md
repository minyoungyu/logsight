# 공개 데이터셋으로 잰 탐지 성능 (독립 측정)

자체 테스트 사이트(lab)에서 낸 재현율 100%는 규칙을 만든 사람이 시나리오도 만든 결과다.
여기서는 **남이 만들고 남이 라벨한** 공개 데이터셋으로 같은 엔진을 잰다.
규칙·파서는 하나도 바꾸지 않았다. 프로필에는 사이트 설명(로그 경로, 자기 호스트 이름, syslog 연도)만 적었다.
측정은 규칙만 쓴다(AI 호출 없음).

## 한눈에 보기

| 측정 | 공격 단계 탐지 | 줄(요청) 단위 재현율 | 정밀도 | 오탐률 | 비고 |
|---|---|---|---|---|---|
| 자체 lab (기존) | 34/34 | - | - | 정상 트래픽 오탐 0건 | 시나리오를 규칙 작성자가 만듦 |
| AIT-LDS v2.0 russellmitchell, 침해된 서버 | **3/7** | 98.7% (7,639/7,739) | 98.2% | 1.8% (142/7,969) | 잡은 건 스캔 3단계뿐, 실제 침투(웹셸 업로드·명령 실행)와 권한 상승은 놓침 |
| AIT-LDS v2.0, 공격 라벨 없는 웹서버 | - | - | - | 0.2% (129/65,290줄), IP 4/6 | 129줄 중 12줄은 실제 공격자 nmap(데이터셋 라벨 누락) |
| HTTP CSIC 2010 | - | - | - | - | **공식 사이트 접속 불가로 측정 못 함** |

**결론: 줄 단위 98.7%는 dirb·wpscan이 남긴 7,600여 줄의 스캔 소음이 만든 숫자다.**
공격 흐름으로 보면 정찰 3단계만 잡았고, 서버를 실제로 장악한 단계(wpDiscuz 업로드 취약점으로 웹셸 올림 → 웹셸로 명령 32회 실행 → su·sudo 권한 상승)는 하나도 잡지 못했다.
전체 판정도 거꾸로 나왔다. 실제로 침해된 intranet_server는 "의심(suspicious)", 공격 라벨이 없는 webserver는 Nextcloud 오탐 때문에 "침해 가능성 높음(likely_breached)"이었다.
자체 lab의 100%는 일반화되지 않는다.

## 1. AIT-LDS v2.0 (russellmitchell 테스트베드)

- 데이터: 가상 회사망에서 정상 사용자 시뮬레이션 4일 + 다단계 공격 1회. 공격 단계별로 로그 줄에 라벨이 붙어 있다.
- 받은 것: 테스트베드 zip(7.1GB)을 통째로 받지 않고 HTTP Range 요청으로 웹(apache2)·인증(auth.log) 로그와 라벨만 41MB 꺼냈다. 디스크에 zip은 남지 않는다.
- 호스트: `intranet_server`(WordPress, 공격 대상), `webserver`(메일·Nextcloud 리버스 프록시, 공격 라벨 없음), `cloud_share`.
- 재현: `python scripts/public/fetch_ait.py --out data/public/ait` → `python scripts/public/eval_ait.py --data data/public/ait --out reports/public/ait_russellmitchell.json`
- 결과 원본: [`reports/public/ait_russellmitchell.json`](../reports/public/ait_russellmitchell.json)

### 공격 단계별 (intranet_server)

| AIT 라벨 | 라벨 줄 | 표시한 줄 | 판정 | 걸린 규칙 |
|---|---|---|---|---|
| service_scan (nmap) | 12 | 6 | 탐지 | WEBLOG_SCANNER, WEBLOG_ENUM_404 |
| dirb (경로 대입) | 4,485 | 4,447 | 탐지 | WEBLOG_ENUM_404, WEBLOG_SENSITIVE_FILE |
| wpscan | 3,199 | 3,186 | 탐지 | WEBLOG_SCANNER, WEBLOG_ENUM_404 |
| webshell_upload (wpDiscuz CVE-2020-24186) | 3 | 0 | **놓침** | - |
| webshell_cmd (웹셸로 명령 실행) | 32 | 0 | **놓침** | - |
| attacker_change_user (su) | 4 | 0 | **놓침** | - (auth 파서가 su 줄을 읽지 않음) |
| escalated_command (sudo) | 5 | 0 | **놓침** | - |

놓친 이유(코드를 고치지 않고 원인만 기록):

1. **웹셸 업로드**: `POST /wp-admin/admin-ajax.php` 200 한 줄뿐이다. 접속 로그에는 본문이 없어서 정상 댓글 요청과 구별되지 않는다. lab의 XXE·저장형 XSS와 같은 사각지대다.
2. **웹셸 명령 실행**: `/wp-content/uploads/2022/01/<임의>.php?wp_meta=<base64 명령>` 형태다.
   - `WEBLOG_UPLOAD_EXEC`는 업로드 폴더를 `/uploads`, `/upload`, `/files`, `/data`로 시작하는 경로로만 본다. WordPress의 `/wp-content/uploads/`는 해당이 안 된다.
   - `SHELL_PARAM`은 `cmd`·`exec` 같은 이름만 보고, 명령이 base64라 `CMDI` 패턴에도 걸리지 않는다.
   - 응답이 매번 약 500KB였는데 `WEBLOG_LARGE_EXFIL`은 같은 요청이 공격 패턴이나 관리자 경로에 걸렸을 때만 보므로 걸리지 않았다.
3. **권한 상승**: auth 파서가 sshd·sudo·useradd만 읽는다. `su` 줄은 이벤트가 되지 않고, sudo 줄은 이벤트는 되지만 sudo 단독으로 걸리는 규칙이 없다.

### 오탐

| 호스트 | 규칙 | 줄 | 원인 |
|---|---|---|---|
| intranet_server | WEBLOG_AUTH_BRUTE | 142 | 정상 사용자의 wpDiscuz 댓글 갱신(`POST /wp-admin/admin-ajax.php`)이 `/wp-admin` 접두사 때문에 관리자 로그인 시도로 세어짐 |
| webserver | WEBLOG_WEBSHELL_ACCESS | 117 | Nextcloud 미리보기 `/remote.php/dav/...?c=<해시>`의 `c=` 인자를 웹셸 명령 인자로 봄 |
| webserver | WEBLOG_LARGE_EXFIL | 5 | 위 오탐 요청 뒤의 큰 이미지 응답 |
| webserver | WEBLOG_SCANNER | 12 | 공격자의 nmap 스캔(03:57, attacks.log의 service_scan과 같은 시각). **실제 공격이지만 AIT가 이 호스트에는 라벨을 달지 않아 오탐으로 셌다** |

`cloud_share`는 접속 로그가 `vhost_combined` 형식(줄 앞에 `호스트:포트`)이라 29,795줄 중 9줄만 읽혔다. 이 형식을 읽지 못하는 것도 결과로 남긴다.

### IP 단위 (ctf_evaluate.py 형식)

`scripts/ctf_evaluate.py`와 같은 정답 형식(`measure.score`)으로도 쟀다. 라벨 줄의 IP를 공격, 나머지 IP를 정상으로 뒀다.

| 호스트 | 재현율 | 정밀도 | 오탐률 |
|---|---|---|---|
| intranet_server | 1/1 | 50% | 1/5 정상 IP |
| webserver | - | 0% | 4/6 정상 IP |

**이 숫자는 참고만 한다.** 이 테스트베드에서는 외부 VPN 사용자와 공격자가 같은 방화벽 NAT 주소(172.19.131.174)로 들어온다. 공격 IP가 곧 정상 사용자 IP라서 IP 단위 재현율 100%는 의미가 없다. 실제 CTF 정답 파일도 팀 NAT를 쓰면 같은 문제가 생긴다.

## 2. HTTP CSIC 2010

- 공식 사이트(`https://www.tic.itefi.csic.es/dataset/`)는 2026-10-25 측정 시점에 HTTPS 연결이 재설정되고, HTTP는 503(upstream connect timeout)을 돌려줬다. 세 번 다시 시도해도 같았다.
- 미러(Kaggle·GitHub 사본)는 출처를 확인할 수 없어 쓰지 않았다.
- 변환·측정 스크립트는 준비해 두었다: `python scripts/public/eval_csic.py --normal normalTrafficTest.txt --anomalous anomalousTrafficTest.txt --out reports/public/csic2010.json`
  - 원시 HTTP 요청을 Apache `combined` 줄로 바꾼다. 응답·IP·시각이 없어 요청마다 다른 IP, 200 응답, 1초 간격을 가정한다(같은 IP 연속 요청 규칙은 이 데이터로 잴 수 없다).
  - 실제 접속 로그에는 POST 본문이 없으므로 **본문 제외(현실)**와 **본문 포함(상한)** 두 번 잰다.
  - 합성 요청 4개로 변환이 맞는지만 확인했다. 실제 숫자는 사이트가 열리면 낸다.

## 4. 다음에 할 일 (이번에는 하지 않음)
