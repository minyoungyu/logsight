# 실제 ufw 방화벽 로그로 서버 방화벽 파서 확인 (2026-11-13)

## 무엇을 했나
- 리눅스 한 대(Ubuntu 24.04, 커널 6.18) 안에 **실제 ufw 0.36**과 rsyslog를 설치하고, 네트워크 이름공간 하나를 '외부 접속자'로 두어 veth로 연결했다. 클라우드 비용 0원.
- ufw 설정: 기본 차단(들어오는 것), 22·80 허용, 443은 `allow log`(허용도 기록). 22·80·443에는 접속만 받는 가짜 서비스.
- 같은 시나리오를 `ufw logging low`(Ubuntu 기본)·`medium`·`full` 세 단계로 돌렸다.
  - 정상 사용자(198.51.100.77): HTTP 5회, HTTPS 1회
  - 공격자(203.0.113.50): ping 3회 → TCP 22개 포트·UDP 4개 포트 스캔 → SSH 연속 접속 25회 → 웹 경로 5개(`/.env`, `/.git/config` 등) + HTTPS
  - 서버(203.0.113.10)에서 공격자 4444 포트로 나가는 연결 1회(역방향 셸 모양)
- 재현: `sudo bash lab/ufw/run.sh` (약 4분, 이 컴퓨터의 ufw 설정을 바꾸니 실습용 가상머신에서). 결과는 `lab/ufw/out/`.
- 저장소에 넣은 표본: `tests/fixtures/ufw/` (rsyslog 기본 ISO 시각 형식 3개 + 예전 `Nov 13 11:12:21` 형식 1개).
  주소는 처음부터 문서용 대역(RFC 5737)이고, 호스트 이름은 `web1`, 인터페이스는 `eth0`, MAC은 문서용 MAC(00:00:5e:00:53:xx)으로 바꿨다. 이 컴퓨터의 다른 통신 줄은 뺐다.

## 실제 로그에서 처음 알게 된 것 (합성 표본에는 없던 것)
1. **`[UFW AUDIT]`는 허용이 아니다.** logging medium 이상에서 판정 전에 새 연결마다 남는다. 차단될 패킷도 AUDIT 줄 다음에 BLOCK 줄이 또 남는다. 이전 파서는 AUDIT을 '서버까지 도달(accept)'로 읽어, medium 표본에서 차단된 21·23 포트 접속이 허용으로도 한 번 더 세어졌다.
   → 같은 패킷(출발·도착 주소와 포트, 패킷 ID)에 BLOCK·ALLOW 줄이 있으면 AUDIT 줄은 버린다.
2. **logging full은 연결이 아니라 패킷마다 남긴다.** 서버가 보낸 응답(80 → 상대 임시 포트)까지 AUDIT로 남아, 우리 서버가 '포트 스캔'을 한 것처럼 사건이 하나 더 생겼다. 파서가 출발 포트를 저장하지 않아 기존의 '응답 빼기'(`detect._is_reply`)도 작동하지 않았다.
   → TCP AUDIT 줄은 연결 시작(SYN만 있고 ACK 없음)만 이벤트로 만들고, 출발 포트를 `extra.src_port`에 넣는다.
3. **ufw는 NetBIOS·SMB·DHCP(137·138·139·445·67·68)를 기록 없이 버린다.** 그래서 139·445 스캔은 AUDIT 줄만 남고 BLOCK 줄이 없다. 이전 파서는 이것을 허용으로 읽었다.
   → 이 포트의 AUDIT 줄은 차단(reject)으로 본다(기본 정책이 차단이라는 가정).
4. **기본(low)에서는 허용된 접속이 거의 안 남는다.** SSH 25회 접속은 low 로그에 한 줄도 없다. `allow log`로 연 443만 남는다. 그래서 low만으로는 `VPC_REMOTE_ADMIN_EXPOSED`(관리 포트 허용)가 뜨지 않는다.
5. **ufw는 줄 종류마다 분당 3건, 한 번에 10건까지만 기록한다(full 제외).** 스캔 26개 포트 중 low·medium에서는 차단 10줄만 남았다. 서버의 다른 통신이 한도를 먼저 써 버리면 공격 줄이 더 줄어든다. AUDIT 줄은 남고 BLOCK 줄이 한도에 걸려 빠지면, 그 접속은 여전히 허용으로 읽힌다(로그만으로는 구분할 수 없음).

## 사용자에게 권할 설정
- 가장 단순: `sudo ufw logging low` 그대로 두고, 관리 포트는 `sudo ufw allow log 22/tcp`처럼 `log`를 붙여 연다. 차단과 관리 포트 접속이 모두 남는다.
- 한도 없이 다 보려면 `scripts/setup_hostfw_log.sh`(새 연결만, 분당 30건) 또는 `ufw logging full`(패킷마다라 로그가 많음, 이번 시나리오에서 low의 30배).

## 남은 한계
- 보안그룹이 막은 패킷은 서버까지 오지 않아 안 보인다(기존과 같음).
- 실제 인터넷 스캐너 흔적은 아니다. AWS 실습(보류 중)이나 공인 IP가 있는 서버에서 며칠 켜 두어야 얻을 수 있다.
- IPv6는 끄고 돌렸다(`IPV6=no`). ufw IPv6 줄(`SRC=2001:db8::...`)은 확인하지 않았다.
