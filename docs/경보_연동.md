# 경보 연동: AWS 경보가 오면 분석을 자동으로 돌리기

구상한 동작 흐름 1단계("AWS에서 경보가 나면 분석 서버의 LogSight 엔진이 쌓인 로그로 산출물을 즉시 만든다")를
구현한 것이다. 2단계(통지)는 이 기능의 `--notify-cmd` 자리에 붙인다. 3단계(자동 격리)는 `--respond`를 줄 때만 켜지고
설명은 `docs/자동_격리.md`, 로그를 계정 밖에 지울 수 없게 보관하고 서버 로그 끊김을 감시하는 것은 `docs/수집_보호.md`.
**`--respond` 없이 돌리면 이 연동은 AWS 설정을 바꾸지 않는다.** 대기열에서 경보를 받고 지우는 일과 로그를 읽는 일만 한다.

## 구조

    AWS 계정                                         분석 서버(팀원 PC 또는 별도 서버)
    GuardDuty 결과 (중간 이상) ─┐
    CloudWatch 경보 (ALARM)    ─┼→ EventBridge 규칙 → SQS 대기열 ←── logsight watch (20초 긴 폴링)
    위험 API 호출 (CloudTrail) ─┘         (3번 실패 → 실패 대기열)     → 경보 앞뒤 로그 모으기
                                                                        로컬 폴더 + S3(날짜 폴더만)
                                                                      → 분석 → 보고서·요약
                                                                      → --notify-cmd (통지 연결 지점)

SQS를 고른 이유:

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **SQS 대기열 + 분석 서버가 가져감** (채택) | 분석 서버에 들어오는 포트가 필요 없다(팀원 PC도 됨). 서버가 꺼져 있던 동안의 경보가 4일까지 남는다. 실패하면 다시 시도, 3번 실패하면 실패 대기열 | 최대 20초 늦을 수 있다(긴 폴링) |
| EventBridge API destination → 분석 서버 HTTPS 주소 | 바로 온다 | 분석 서버를 인터넷에 열어야 하고, 인증·재시도를 따로 만들어야 한다 |
| Lambda에서 직접 분석 | 서버가 필요 없다 | 분석 코드·의존성을 Lambda에 올려야 하고, 고객 계정 안에서 돈다(로그를 밖에 두는 4단계와 충돌) |

## 무엇이 분석을 시작하나

| 경보 | 등급 | 기본 동작 |
| --- | --- | --- |
| GuardDuty 결과 | 점수 7 이상 높음, 4 이상 중간, 나머지 낮음 | 중간 이상이면 분석(`--min-severity`) |
| CloudWatch 경보가 ALARM이 됨 | 이름에 critical/high가 있으면 높음, low면 낮음, 나머지 중간 | 분석 |
| 위험 API 호출 | 로그 끄기·지우기(StopLogging, DeleteTrail, DeleteDetector 등)는 높음, 키·사용자 생성과 권한 변경은 중간 | 분석 |
| Security Hub 결과 | 라벨 그대로 | 템플릿에는 없음(이벤트 형식만 읽음) |

같은 경보가 60분 안에 또 오면 다시 분석하지 않는다(`--cooldown`). GuardDuty는 같은 결과가 반복되면
같은 ID로 갱신 이벤트를 보내기 때문이다. 경보 해제(OK) 이벤트, 경보가 아닌 메시지는 지우고 넘어간다.

분석 기간은 "활동이 처음 보인 시각(GuardDuty `eventFirstSeen`)보다 24시간 앞"부터 "받은 시각 + 5분"까지다
(`--lookback-hours`). GuardDuty 결과와 위험 API 호출 이벤트는 그 자체도 분석 입력으로 넣는다.

## 설치

1. AWS에 템플릿을 올린다(콘솔 CloudFormation 또는 CLI). 기존 자원은 건드리지 않고 대기열·규칙·읽기 정책만 만든다.

       aws cloudformation deploy --template-file deploy/aws/logsight-alerts.yaml \
         --stack-name logsight --capabilities CAPABILITY_IAM \
         --parameter-overrides MinGuardDutySeverity=MEDIUM LogBucketName=<로그 버킷> ConsumerRoleName=<분석 서버 역할>

   IAM 호출(CreateAccessKey 등)은 EventBridge에 us-east-1로만 전달된다. 이것까지 받으려면 us-east-1에도
   같은 템플릿을 올린다(대기열이 둘이 되므로 `watch`를 둘 돌리거나, 한쪽 규칙의 대상을 다른 리전 대기열로 바꾼다).

2. 분석 서버에서 감시를 시작한다. 출력 `WatchCommand`를 그대로 쓰면 된다.

       python -m logsight watch --queue-url <QueueUrl> --region ap-northeast-2 \
         --logs /var/logsight/host-logs \
         --s3 "s3://<로그 버킷>/AWSLogs/<계정>/CloudTrail/ap-northeast-2/{date}/" \
         --s3 "s3://<로그 버킷>/AWSLogs/<계정>/vpcflowlogs/ap-northeast-2/{date}/" \
         --env environment.json --out reports/alerts \
         --notify-cmd "python notify.py"

   `{date}`는 기간의 날짜마다 `YYYY/MM/DD`로 바뀌어 그날 폴더만 읽는다(버킷 전체를 훑지 않음).
   `--collect-env`를 주면 경보 때마다 설정 스냅샷을 새로 읽는다(읽기 전용 권한 필요).
   서버에 상주시키려면 systemd 서비스나 `tmux`로 돌린다. Ctrl+C로 끝난다.

3. 결과는 경보마다 폴더 하나다.

       reports/alerts/20261104_142606_guardduty_2019c894/
         report.html  report.json   보고서(analyze와 같은 형식)
         summary.txt                통지용 요약(10줄 안팎, 원본 로그·키 없음)
         alert.json                 받은 경보
         run.json                   수신 시각, 보고서 시각, 걸린 시간, 분석 기간, 읽은 로그
         inputs/                    경보 자체와 S3에서 받은 로그

통지는 `--notify notify.json`으로 이메일·디스코드·슬랙·일반 웹훅 중 골라 쓴다(`docs/통지.md`).
그 밖의 수단은 `--notify-cmd`로 붙인다. 명령은 셸을 거치지 않고 실행되며, 환경변수 `LOGSIGHT_SUMMARY`(요약 파일 경로),
`LOGSIGHT_REPORT_DIR`, `LOGSIGHT_SEVERITY`, `LOGSIGHT_ALERT_ID`를 받는다.

## 시험해 보기 (AWS 없이)

    python -m logsight on-alert samples/alerts/guardduty_event.json --logs samples/demo --no-ai

`samples/alerts/guardduty_event.json`은 `samples/guardduty`의 첫 결과를 EventBridge 형식(camelCase)으로 바꾼 합성 이벤트다.

## 측정한 것과 아닌 것

| 항목 | 상태 |
| --- | --- |
| 경보 해석(GuardDuty·CloudWatch·CloudTrail·SNS 감싼 형식), 등급 기준, 중복 무시, 기간 거르기, 통지 명령 | 단위 테스트(`tests/test_alert.py`) |
| SQS 받기 → 분석 → 지우기, 경보 아닌 메시지 지우기, 실패 시 남기기 | moto(가짜 AWS)로 시험 |
| S3 날짜 폴더만 받기 | moto로 시험 |
| 받은 뒤 보고서까지 걸린 시간 | 저장소 샘플(이벤트 12건·88건)로 0.1초 미만, AI 끔. 실제 로그 규모·AI 켬은 미측정 |
| CloudFormation 템플릿 | cfn-lint 통과. **실제 계정에 올려 본 적 없음** |
| EventBridge 규칙이 실제 경보와 맞는지, 경보 발생 → 대기열 도착 시간 | **미측정**(실제 계정 필요) |

알려진 한계:

- CloudTrail은 약 5분, VPC Flow Logs는 약 10분 늦게 S3에 쌓인다. 경보 직후 바로 분석하면 경보 직전 몇 분의
  로그가 빠질 수 있다. 요약에 이 문장을 넣었다. 나중에 같은 경보를 15분 뒤 한 번 더 분석하는 방안을 검토한다.
- 같은 결과가 로컬 폴더(예: guardduty_findings.json)에도 있으면 경보와 겹쳐 두 번 셀 수 있다.
- 서버 안쪽 로그(nginx, auth.log)는 `docs/수집_보호.md`의 Fluent Bit 설정으로 보관 버킷 `hosts/`에 올리고 `--s3`로 읽는다.
