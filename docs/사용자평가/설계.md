# 사용자 평가 설계: 보안 비전문가도 LogSight로 사고를 판단할 수 있나

LogSight의 핵심 주장은 "보안 담당자가 없는 작은 팀도 경보 뒤에 무슨 일이 있었고 무엇을 고칠지 판단할 수 있다"이다.
지금까지의 측정은 모두 **엔진이 무엇을 잡나**였고, **사람이 더 잘 판단하나**는 잰 적이 없다.
이 문서는 그것을 재는 작은 실험의 설계다. 팀이 그대로 진행할 수 있게 질문지·정답·채점기준·집계 스크립트를 함께 둔다.

비슷한 틀: Cloud Security Alliance와 Dropzone AI의 연구(2025)는 148명을 AI 사용·미사용 그룹으로 나눠 AWS S3 경보 등 2개 시나리오를
전문가 모범답안과 비교해 정확도·속도를 쟀다. 여기서는 인원이 적으므로 **한 사람이 두 조건을 모두 하는 교차 설계**를 쓴다.

## 1. 가설과 측정값

- 가설: 같은 사람이 같은 난이도의 사고를 볼 때, LogSight 보고서가 있으면 **정답 점수가 높고 시간이 짧다.**
- 주 측정값: 정답 점수(10점 만점, [정답_채점기준.md](정답_채점기준.md))
- 보조 측정값: 제출까지 걸린 시간(분), 확신도(1~5)와 실제 점수의 차이, 정상 활동을 공격으로 잘못 지목한 수

## 2. 참가자

- 8명 이상(조건 순서를 맞추려면 4의 배수). 개발·운영 경험은 있지만 **보안 담당 경험이 없는** 사람.
  예: 학과·동아리 개발자, 스타트업 개발자. 작은 팀의 실제 사용자와 가까운 사람이다.
- **팀원과 측정 데이터를 본 사람은 제외**한다. 정답을 알고 있기 때문이다.
- 사전 설문: 경력(년), AWS 사용 경험(없음/조금/업무), 보안 교육 경험. 결과를 나눠 볼 때만 쓴다.
- 동의서를 받고, 결과는 참가자 번호(P01…)로만 적는다. 이름·연락처는 결과 파일에 넣지 않는다.

## 3. 시나리오와 조건

| 시나리오 | 데이터 | 무엇이 있었나(참가자에게는 비공개) |
|---|---|---|
| A | 클라우드 공방전 로그(가명 처리, `data/gongbang`) | 웹앱의 내부 주소 조회로 EC2 역할 키를 얻어 외부에서 사용. 정상인 블루팀 조회 작업이 섞여 있음 |
| B | 공개 데이터 BOTSv3의 AWS 부분(`scripts/public/botsv3_extract.py`로 추출) | 유출된 IAM 키로 권한 탐색·생성 시도(실패), 직원 실수로 S3 버킷 공개, 인터넷 SSH 스캐너 |

| 조건 | 참가자가 받는 것 |
|---|---|
| 기존 방식 | 원본 로그 파일 + 평소 쓰는 도구(편집기, 스프레드시트, jq 등) + GuardDuty 결과(있으면) |
| LogSight | 같은 원본 로그 + LogSight 보고서(HTML, AI 없이 규칙 모드) |

"기존 방식"은 GuardDuty만 쓰는 작은 팀이 경보를 받은 뒤 하는 일과 같게 맞췄다. LogSight 쪽에도 원본 로그를 준다.

### 순서 맞추기(교차 설계)
한 사람이 두 시나리오를 서로 다른 조건으로 한다. 순서 효과를 없애려고 4개 묶음에 고르게 배정한다.

| 묶음 | 첫 번째 | 두 번째 |
|---|---|---|
| 1 | A · LogSight | B · 기존 방식 |
| 2 | A · 기존 방식 | B · LogSight |
| 3 | B · LogSight | A · 기존 방식 |
| 4 | B · 기존 방식 | A · LogSight |

## 4. 진행(한 사람 약 70분)

1. 동의서, 사전 설문(5분)
2. 연습(10분): 작은 합성 예제(`samples/demo`)로 두 조건의 화면·파일을 익힌다. 정답은 알려 주지 않는다.
3. 첫 번째 시나리오(최대 25분): 상황 설명 한 줄("어제 이 AWS 계정에서 이상한 일이 있었다는 신고를 받았습니다")과 함께 자료를 주고
   [질문지.md](질문지.md)에 답하게 한다. 끝났다고 말한 시각을 적는다. 25분이 되면 그대로 걷는다.
4. 쉬기(5분)
5. 두 번째 시나리오(최대 25분)
6. 사후 설문(5분): 어느 쪽이 쉬웠나, LogSight 보고서에서 믿기 어려웠던 부분, 없어서 아쉬웠던 정보

진행자는 내용 질문에 답하지 않는다. 인터넷 검색은 금지한다(BOTSv3 풀이가 공개돼 있다).

## 5. 채점

- 채점자 2명이 [정답_채점기준.md](정답_채점기준.md)로 문항마다 0·1·2점을 준다. **채점자는 답안이 어느 조건인지 모른다**
  (진행자가 답안지의 조건 표시를 가리고 번호만 붙여 넘긴다).
- 두 채점자의 점수가 2점 이상 차이 나는 문항은 함께 다시 보고 합의한다. 일치율(같은 점수를 준 문항 비율)을 결과에 적는다.
- 결과는 [응답_양식.csv](응답_양식.csv)에 한 줄씩 넣고 `python scripts/study_score.py docs/사용자평가/응답.csv`로 집계한다.

## 6. 분석과 해석 기준

- 사람마다 (LogSight 점수 − 기존 방식 점수)와 (시간 차이)를 구한다. 같은 사람 안에서 비교하므로 실력 차이가 상쇄된다.
- 차이의 중앙값과 사람별 값을 모두 보여 준다. 8명이면 통계적 결론은 약하므로, 부호 뒤집기 정확검정 p값은 참고로만 적는다.
- 시나리오 난이도 차이는 시나리오별 평균으로 따로 적는다(A가 B보다 어려울 수 있다).
- **미리 정한 성공 기준**: 8명 중 6명 이상이 LogSight 조건에서 점수가 같거나 높고, 점수 차이 중앙값이 +2점 이상.
  기준에 못 미치면 그대로 발표한다. 어느 문항에서 졌는지가 다음 개선 목록이 된다.
- 잘못된 확신을 따로 본다: LogSight 조건에서 확신도는 높은데 점수가 낮다면, 보고서가 틀린 판정을 그럴듯하게 보이게 한 것이다.

## 7. 알려진 한계

- 인원이 적고 참가자가 실제 고객이 아니다. "작은 팀 개발자"에 가까운 사람을 고르는 것으로 보완한다.
- 시나리오 B는 엔진을 BOTSv3에 맞춰 고친 뒤라 LogSight에 유리할 수 있다. 시나리오 A도 공방전 측정 뒤 고쳤다.
  가능하면 세 번째 시나리오로 처음 보는 데이터(예: Splunk attack_data의 여러 표본을 섞은 것)를 추가한다.
- 진행자가 팀원이면 기대 효과가 생긴다. 진행 대본을 그대로 읽고, 가능하면 팀 밖 사람이 진행한다.
