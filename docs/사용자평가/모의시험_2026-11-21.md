# 모의 사용자 시험: 보안 경험 없는 개발자 10명(가상)으로 보고서와 사양서 읽히기 (2026-11-21)

> **이 문서는 실제 사용자 시험이 아니다.** 참가자 10명은 Claude가 만든 가상 인물이고, 답과 점수는 실제 보고서 문장을 근거로 한 **예측**이다.
> S3·NFR-16(비전문가 이해)의 증거로 쓰지 않는다. 쓸모는 두 가지다. (1) 실제 시험 전에 보고서·사양서에서 막힐 곳을 미리 찾아 고친다.
> (2) 실제 시험에서 확인할 **가설 목록**을 미리 적어 둔다(아래 6절). 실제 8명 교차 시험([설계.md](설계.md))은 그대로 해야 한다.

## 4. 인물별 진행 (보고서 문장 근거)

인용은 실제 보고서 문장이다. 인물의 말은 가상이다.

**P01** — 끝까지 읽고 `auth.log`를 직접 열어 `Accepted password for ubuntu`를 찾음. 수정안의 "IMDSv1 허용"을 보고 역할 키가 서버 메타데이터에서 나갔다고 이어 붙임.
막힌 곳: "탈취 의심 계정 잠그고 비밀번호·키 교체 · account · (서버)"에 계정 이름이 없어 원본을 열어야 했다. "보고서만 줬다면 root라고 썼을 것."
T1 10점(22분), T2 6점.

**P02** — 휴대폰 첫 화면이 머리말·문서 정보(분석 방식, 분석 대상, 작성 일시)로 꽉 차 결론이 안 보임. 데스크톱으로 옮겨 "먼저 할 일" 위 두 줄만 봄.
2번에 "SQL 인젝션"이라고 씀: 단계별 설명에서 **초기 침투 T1190 "SQL 인젝션 요청 1건을 WAF가 알아봤지만 기록만 하고 통과시켰습니다"**가 SSH 로그인보다 먼저 나오고,
"서버가 오류(500)로 응답했습니다. 취약한 코드가 실제로 건드려졌다는 신호" 문장이 성공처럼 읽힘. INC-003(심각도 낮음, 막힘 1건)도 "공격 의심"이라 침입으로 적음(오지목 1).
T1 5점(9분, 확신 4), T2 4점.

**P03** — "IMDSv1", "COUNT(기록만) 모드", "NACL", "T1552.005"에서 멈춤. "임시 자격증명이 서버를 꺼도 작동한다"는 설명은 이해했지만 우선순위가 4번째라 조치에는 22번 포트와 WAF를 씀.
2번은 SQL 인젝션과 SSH 둘 다 적음. T1 7점(17분), T2 4점.

**P04** — "역할 키로 API 3번: s3:ListBuckets, s3:GetObject, iam:CreateUser · 성공 2 · 실패 1" 표에서 바로 4번을 맞힘.
다음 질문에서 멈춤: "**무슨 버킷의 무슨 파일을 가져갔나?** 이걸 모르면 대표에게 보고를 못 한다." 보고서는 대상을 말하지 않고, 로그에도 없다는 말도 없음.
웹 점검에서는 "침해 확인" 판정 바로 아래 "공격 성공을 로그만으로 단정하기 어렵다"를 보고 1번을 "모르겠다, 뚫린 것 같다"로 흐림. T1 8점(19분), T2 3점.

**P05** — 수정안의 명령부터 펼쳐 봄. 세션 무효화와 22번 포트를 고름. 원본도 대조해 10점(15분).
지적: INC-002의 "WAF … COUNT(기록만) 모드" 수정안 근거가 `nginx_access.log:24~27`인데, 그 요청은 WAF 로그에 없음. "WAF를 안 거친 요청인데 WAF를 고치라고?"
T2 6점.

**P06** — 공격 흐름 그림을 오래 봄. 그림에서 "역할 ec2-app-role → S3"를 보고 데이터가 나갔다고 이해. 사이드바의 사건 이름 **"GuardDuty: SSH 비밀번호 연속 실패(무차별 대입)"**만 기억해 1번 근거를 "SSH 비밀번호 대입"으로 씀(1점).
10월의 INC-002를 같은 공격자의 다른 단계로, INC-003을 침입으로 적음(오지목 2). T1 4점(14분), T2 4점.

**P07** — 6분 만에 첫 화면만 보고 제출. "공격 의심 3건"을 사건 3개가 다 심각하다고 읽음. 먼저 할 일 5개가 모두 "즉시"라 위에서부터 둘(22번, WAF)을 고르려다 "탈취된 세션 무효화"를 보고 바꿈.
4번은 "모름". 확신 4. **점수(5)보다 확신이 높은 사례**: 첫 화면에 결론 문장이 없고 사건 3개가 같은 무게로 보인다. T2 3점(웹셸 파일 못 찾음).

**P08** — 근거 줄을 원본과 하나씩 대조해 25분을 다 씀. 지적: INC-002 요약은 "성공·허용 7건"인데 같은 사건의 SQL 인젝션 설명은 "성공 근거 없음"이고,
결과 칸의 "성공 3"은 방화벽이 연결을 **허용**한 것(tcp/22 ACCEPT)이라 공격 성공과 다른 뜻. "'성공'이라는 말이 세 가지 뜻으로 쓰인다." T1 9점, T2 6점.

**P09** — 용어에서 계속 막힘(역할, 임시 자격증명, 메타데이터, NACL, 무차별 대입). "확신도 높음"이 누구의 확신인지 모름. 웹 점검의 "업로드 폴더의 스크립트 실행 — 3건"을 보고 파일 이름을 찾으러 갔지만
조치안의 "**표시된 파일을** 삭제하지 말고 먼저 복사해 보관"에서 표시된 파일이 어디에도 없음(근거 로그를 펼쳐야 `shell.phtml`이 나옴). T1 4점(21분, 확신 2), T2 2점.

**P10** — ATT&CK 번호(T1190, T1133 …)를 "검색해야 하는 잡음"이라 함. 시간이 웹 보고서는 `2026-10-22T03:59:34` UTC만 있고 사후 분석 보고서는 한국 시간도 있어 헷갈림. T1 7점, T2 4점.

## 7. 한계 (꼭 읽을 것)

- **사람이 아니다.** 가상 인물의 답은 한 모델이 만든 것이라 서로 독립이 아니고, 실제 사람의 실수(오독, 피로, 엉뚱한 확신)를 다 담지 못한다.
- **정답을 아는 쪽이 만들었다.** 보고서의 문제를 먼저 찾은 뒤 인물을 돌렸으므로, 찾은 문제 쪽으로 점수가 기울었을 수 있다. 점수의 절대값은 믿지 말고 **막힌 곳의 목록**만 쓴다.
- **시간은 어림값이다.** 읽은 양으로 추정했고 측정하지 않았다.
- **시나리오가 다르다.** 실제 시험의 A(공방전)·B(BOTSv3)가 아니라 저장소 샘플을 썼다. 샘플은 우리가 만든 데이터다.
- **비교 조건이 없다.** "기존 방식"(원본 로그만) 조건을 돌리지 않았으므로 LogSight가 더 낫다는 근거가 아니다.

참고 파일: 첫 화면 캡처와 보고서 문장은 이 시험을 돌린 작업 공간에만 있고 저장소에는 넣지 않았다(같은 명령으로 다시 만들 수 있다:
`python -m logsight analyze samples/combined --no-ai`, `python -m logsight scan samples/web --no-ai`).
