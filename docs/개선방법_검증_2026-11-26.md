## S7(오탐) 방법

### 방법 1. 규칙 성숙도: 새 규칙은 "시험 중"으로 두고 경보에서 뺀다 — **추천**

- **근거 [확인]:**
  - **Sigma 규칙 규격**은 status를 stable·test·experimental로 나눠요. experimental은 "오탐이 나거나 시끄러울 수 있는" 규칙으로 정의해요(SigmaHQ/sigma-specification, sigma-rules-specification.md "Status").
  - **Elastic**의 building block 규칙은 Alerts 표에서 기본으로 숨겨진 경보를 만들어요(elastic.co, About building block rules).
  - **Splunk**는 TTP만 기본 경보를 만들고, Anomaly·Hunting은 위험 점수만 올려요(근거_점검 문서에서 확인한 Splunk ESCU 문서).
- **우리 데이터로 본 효과 [개발, 사후 계산]:** ROBOTS_HIDDEN은 EClog 측정 이틀 전(11/24, a673043)에 들어왔어요. 이 규칙이 "시험 중"이었다면 EClog에서 경보로 센 줄은 9줄이고 모두 실제 공격이에요. 그러면 오탐은 0/350,674(95% 상한 약 0.001%)예요. 결과를 보고 한 계산이라 판정에는 쓸 수 없어요.
- **조건:** S7을 "경보 규칙(stable)의 줄"로 센다면 **CTF 측정 전에 계획 파일에 적어야** 해요. 시험 중 규칙의 줄 수도 결과에 함께 적어야 해요. 그렇지 않으면 숫자를 좋게 보이려고 지표를 바꾼 것이 돼요.
- **승격 기준(제안):** 오탐 검사(fp_gate) 정상 데이터 3개 이상에서 오탐 0.01% 이하이고, 외부 데이터에서 실제 공격을 1번 이상 잡으면 stable로 올려요.

### 방법 2. 병합 전 오탐 검사 — 이미 했음
- `scripts/public/fp_gate.py`(f290782)가 규칙별 오탐이 늘면 실패해요. 이 검사가 11/24에 있었다면 ROBOTS_HIDDEN은 EClog에서 1,740줄이 늘어 실패했을 거예요 [개발].

### 방법 3. 크롤러 확인을 User-Agent 대신 DNS·IP 목록으로
- **근거 [확인]:** Google은 요청이 진짜 Google인지 확인하는 방법으로 역방향 DNS 뒤 순방향 DNS 대조와, 공개 IP 범위 JSON(common-crawlers.json 등) 대조를 안내해요(developers.google.com, Google 크롤러 및 가져오기 도구의 요청 확인).
- **한계:**
  - 11/25 수정은 User-Agent에 bot·crawler가 들어 있으면 빼는 방식이라, 공격자가 UA를 꾸미면 빠져나갈 수 있어요.
  - EClog의 오탐 크롤러(TurnitinBot, MJ12bot, SemrushBot)가 IP 목록을 공개하는지는 확인하지 못했어요 [추정].
  - 지난 로그를 분석할 때 DNS 조회 결과는 그 시점과 다를 수 있어요.
- **결론:** Google·Bing 같은 큰 검색엔진은 IP 목록으로 확인하고, 나머지 자칭 크롤러는 "시험 중" 규칙에서만 빼는 정도가 맞아요. 우선순위는 방법 1보다 낮아요.

### 방법 4. 설치할 때 사무실·VPN IP(trusted_ips) 묻기 — 효과가 제한적
- AIT의 ADMIN_ACCESS 오탐 30줄은 공격자와 직원이 **같은 NAT 주소**에서 나와요 [확인: 근거 점검 문서]. 그래서 trusted_ips에 넣으면 공격도 함께 가려져요. 실제 고객에게는 도움이 되지만 이 데이터의 숫자는 바뀌지 않아요.

## S6(처음 보는 데이터) 방법

### 방법 5. 여러 외부 규칙 목록이 함께 다루는 API부터 보강 — **추천**
- **선택 기준:** Panther 놓침 목록(시험 데이터)이 아니라, **서로 독립된 공개 규칙 목록 2곳 이상**이 탐지하는 CloudTrail API를 골라요. 시험 데이터에 맞추는 과적합을 피하기 위해서예요.
- **확인 [확인]:**
  - SigmaHQ/sigma 876eb7b(rules/cloud/aws, 58개), elastic/detection-rules 06a05eb(rules/integrations/aws), splunk/security_content 689e177(detections/cloud)의 eventName을 뽑았어요.
  - 2곳 이상에 나오는 API는 50개예요(`scripts/public/catalog_coverage.py`).
- **지금 LogFinder에 없는 묶음** [확인: 이벤트 하나를 넣어 규칙이 안 걸림 + 코드에 해당 API 없음]:
  - VM·데이터 반출: `ec2:CreateInstanceExportTask`, `s3:PutBucketReplication`(사양서에도 "다른 계정 복제는 보지 않음"이라고 적혀 있음)
  - 파괴: `kms:DeleteImportedKeyMaterial`, `elasticfilesystem:DeleteFileSystem`
  - 키 정책 공개: `kms:PutKeyPolicy`(외부 계정·* 허용)
  - 실행: `ecs:RegisterTaskDefinition`
  - 자격 증명 남용: `sts:GetSessionToken`, `signin:GetSigninToken`, TruffleHog UA의 `sts:GetCallerIdentity`
  - LLM 도용: `bedrock:InvokeModel`
  - S3: MFA 삭제 끄기(`PutBucketVersioning`의 MFADelete), 다른 계정 버킷으로 `CopyObject`
- **기대 효과 [개발, 상한]:** Panther B에서 놓친 30개 중 9개가 이 API를 써요. 9개를 모두 맞게 잡으면 B는 33/56 = 59%가 되고, 4개 이상이면 50%를 넘어요. 다만 B는 이미 판정에 썼으니 이 숫자도 개발 점수이고, 실제 판정에는 새 데이터가 필요해요.

### 방법 6. 새 처음 보는 AWS 데이터 확보 — 판정에 꼭 필요
| 후보 | 상태 |

| Stratus·Invictus | 이미 본 데이터라 쓸 수 없음 |
| Panther A·B | 둘 다 판정에 씀 |

### 방법 7. 지표 확인 — 바꾸지 않음
- 시험 이벤트를 하나씩 넣는 측정이라, 반복·순서로 판단하는 규칙은 걸릴 수 없어요(ManyPasswordReadAttempts, IMDSCredentialExfiltration 등). 숫자가 실제보다 낮게 나올 수 있어요 [추정].
- 그래도 이미 정한 지표는 바꾸지 않아요. 바꾸려면 새 데이터를 재기 전에 계획 파일에 적어야 해요.
