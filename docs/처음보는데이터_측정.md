# 처음 보는 데이터로 잰 결과 (규칙 고정 후 한 번 측정)

지금까지 공방전과 BOTSv3는 **데이터를 보고 나서 규칙을 고쳤다.** 그래서 그 점수는 "개발 과정"이지 실력이 아니다.
여기서는 업계 방식(Splunk·Elastic처럼 규칙을 고정하고, 개발에 쓰지 않은 데이터로 잰다)을 따른다.

- **규칙 고정**: 커밋 `20e4562`(main, 2026-11-03). 측정 전에 규칙을 바꾸지 않았고, 측정 뒤에도 이 결과 파일은 다시 만들지 않는다.
- **데이터**: Splunk Security Content(Apache-2.0)의 AWS 탐지 규칙 52개가 각자 가리키는 시험용 CloudTrail 로그(Splunk attack_data).
  표본마다 "이 로그에는 이 행동이 들어 있다"는 라벨이 붙은 셈이다. 우리 팀은 이 데이터를 처음 받았다.
- **재현**: [`scripts/public/eval_splunk_attack_data.py`](../scripts/public/eval_splunk_attack_data.py) →
  판정 [`scripts/public/judge_splunk_attack_data.py`](../scripts/public/judge_splunk_attack_data.py) →
  결과 [`reports/public/splunk_attack_data.json`](../reports/public/splunk_attack_data.json)
- **판정 기준**(측정 뒤 사람이 표본마다 이유를 적음)
  - 맞게 탐지: LogSight 규칙이 그 행동 자체를 설명한다.
  - 다른 이유로만 걸림: 같은 이벤트가 '루트 사용', 'MFA 없는 로그인' 같은 다른 규칙으로만 표시됐다. 보고서에는 뜨지만 무슨 일인지는 틀리게 말한다.
  - 놓침: 해당하는 표시가 없다.
  - 보조 기준으로, Splunk 규칙이 찾는 API 이름(eventName)이 들어 있는 이벤트를 LogSight가 표시했는지 기계적으로도 기록했다(`target_rules`).

## 결과

| | 탐지 규칙 기준(52) | 서로 다른 표본 기준(44) |
|---|---|---|
| 맞게 탐지 | **16 (31%)** | 14 (32%) |
| 다른 이유로만 걸림 | 8 (15%) | 7 (16%) |
| 놓침 | 28 (54%) | 23 (52%) |

같은 표본을 여러 규칙이 함께 쓰는 경우가 있어 두 기준을 모두 적었다. 결론은 같다.

### 잡은 것: 공격 흐름의 핵심 길목
IAM 사용자·키·권한 만들기(5개 표본), 감사 로그 끄기·지우기와 GuardDuty 끄기(3), 스냅샷·AMI 외부 공유(3), 권한 없는 API 폭주(2),
목록 조회 폭주(1), S3 대량 읽기(1), MFA 없는 콘솔 로그인(1).

### 다른 이유로만 걸린 것: 계정 보안 설정 변경
MFA 끄기·장치 추가·MFA 실패, 비밀번호 정책 변경, 여러 IP 로그인, 콘솔 로그인 연속 실패. 표본이 루트 계정으로 만들어져
'루트 사용'으로 뜨지만, **무엇을 바꿨는지는 말하지 않는다.** 루트가 아닌 계정이었다면 놓쳤을 것이다.

### 놓친 것

| 묶음 | 표본 | 이유 |
|---|---|---|
| 새 서비스 | Bedrock 4, ECR 5, Lambda 코드 변경 1 | 규칙이 EC2·IAM·S3·CloudTrail 중심 |
| 데이터 빼돌리기의 다른 길 | Batch·DataSync·버킷 복제 3, CloudWatch 로그 대량 읽기 1 | GetObject와 스냅샷 공유만 봄 |
| 랜섬웨어·복구 방해 | KMS 암호화 2, 버킷 버전 관리 끄기 1, 수명 주기로 지우기 1 | 규칙 없음 |
| 권한 바꾸기의 다른 길 | SetDefaultPolicyVersion, 정책·그룹 삭제 3, SAML 공급자 변경, AssumeRole 대입 | IAM 규칙 목록 밖 |
| 네트워크 | NACL 전체 개방·삭제 2 | 보안그룹(0.0.0.0/0)만 봄 |
| 서버 접근 | EC2 Instance Connect 키 업로드, 시작 스크립트 변경 | 규칙 없음 |
| 기준 미달 | 거부 1건 | 권한 거부는 10분 5건부터 |

## 개발에 쓴 데이터와 처음 본 데이터

| 데이터 | 처음 봤나 | 결과 |
|---|---|---|
| 자체 실습 환경 | 아니오(시나리오를 우리가 만듦) | 34/34 단계 |
| 클라우드 공방전 로그 | 아니오(측정 뒤 수정) | 사건 판정 4/7, 정상 작업 목록 넣으면 6/7 |

| AIT-LDS 웹서버 | **예** | 공격 단계 3/7(스캔만 잡고 침투는 놓침) |

**처음 본 데이터에서의 실력은 31%와 3/7이다.** 개발 데이터의 높은 점수는 규칙이 의도대로 동작한다는 뜻일 뿐이다.

## 해석과 주의

- Splunk 표본은 "공격 하나의 흐름"이 아니라 **행동 하나씩**이다. 정상 운영에서도 하는 변경(정책 삭제, Lambda 배포)이 많아,
  이것을 모두 잡는 것이 목표는 아니다. 작은 팀에게 경보가 너무 많아지면 안 보게 된다.
- 그래도 계정 보안 설정 변경(MFA·비밀번호 정책·SAML), 랜섬웨어(KMS), 다른 유출 길(복제·DataSync), NACL은
  침해 대응에서 꼭 봐야 하는 것이라 규칙 추가 후보다. [규칙_명세.md](규칙_명세.md)의 사각지대에 `[측정]`으로 적었다.
- 이 측정은 **탐지 범위**만 잰다. 사건 묶기, 판정, 설명이 사람에게 도움이 되는지는 [사용자 평가](사용자평가/설계.md)가 잰다.

## 다음 측정의 규칙

1. 규칙을 고친 뒤 이 표본으로 다시 재면 "개발 데이터"가 된다. 그 숫자는 이 문서의 31%를 대체하지 않고 따로 적는다.
2. 다음 처음 보는 데이터는 미리 고르고 손대지 않는다. 후보: Splunk attack_data에 이 날짜 뒤 새로 추가되는 AWS 표본,
   또는 다른 기관이 공개한 AWS 침해 로그.
3. 측정 전에 규칙 고정 커밋을 이 문서처럼 적는다.
