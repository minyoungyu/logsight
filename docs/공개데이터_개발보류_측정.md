# 처음 보는 공개 데이터: 개발용·보류용으로 나눠 잰 결과 (2026-11-24)

[처음보는데이터_측정](처음보는데이터_측정.md)은 한 번 재고 끝났다. 이번에는 **고치는 데 쓴 데이터(개발용)** 와
**고치는 동안 열어 보지 않은 데이터(보류용, holdout)** 를 미리 나누고, 고치기 전과 뒤에 한 번씩만 쟀다.
개발용 점수는 데이터를 보고 고쳤으니 오를 수밖에 없다. 객관적인 숫자는 보류용 쪽이다.

## 절차

1. **엔진 고정**: 커밋 `0c383aa`(PR #54 머리)에서 모든 데이터를 먼저 쟀다.
2. **나누기를 먼저 기록**: 고치기 전에 [`reports/public/holdout_plan_2026-11-24.json`](../reports/public/holdout_plan_2026-11-24.json)을 썼다
   (sha256 `48a04b45fe4be96f0251e493ffc6f4af086d61c799f6ce4df0ad3f5918160dd8`, 18:00 UTC).
   - 개발용: AIT-LDS v2 `wardbeck`, `wilson`, 그리고 Splunk attack_data 중 처음 재는 15개 규칙
   - 보류용: AIT-LDS v2 `harrison`, `shaw`. 고치는 동안에는 전체 점수 줄만 보고 놓친 줄·오탐 줄은 열지 않았다.
3. 개발용의 놓침·오탐만 보고 고쳤다(아래 3건). 합성 시험 8개를 더하고 전체 시험이 통과했다.
4. 고친 뒤 개발용과 보류용을 **한 번씩** 다시 쟀다. 보류용은 이제 '본 데이터'라서 다음 고침에는 새 보류용이 필요하다.

데이터: AIT-LDS v2.0(Landauer 외, DOI 10.5281/zenodo.5789064, CC BY-NC-SA 4.0. 저장소에는 결과 숫자만 둔다),
Splunk security_content·attack_data(Apache-2.0). `rbd` 테스트베드는 내려받기 주소가 404라 뺐다.

## 측정 도구 오류 하나

Splunk 규칙 파일에서 시험 데이터 주소를 읽는 정규식이 `data:`와 `sourcetype:` 사이에 `source:` 줄이 있는 파일을 건너뛰었다.
그래서 11/3 측정의 52개에는 원래 들어가야 할 규칙 10개가 빠져 있었다(분모가 불완전). 고친 뒤
([`scripts/public/eval_splunk_attack_data.py`](../scripts/public/eval_splunk_attack_data.py)) 처음 재는 15개를 따로 쟀다.
11/3 결과 파일은 다시 만들지 않았다.

## 고친 것(개발용에서 찾음)

| 무엇 | 찾은 곳 | 고침 |
|---|---|---|
| 웹셸 계정 `www-data`가 `su blord` 한 뒤 `blord`의 `sudo cat /etc/shadow`, `sudo ls -laR /root/`를 놓침 | AIT wardbeck·wilson `escalated_command` | `HOST_PRIV_ESC`: 웹 서비스 계정이 su로 넘어간 계정의 그 뒤 sudo, 그리고 sudo로 `/etc/shadow`·`/root/.ssh/`를 읽는 명령도 권한 상승으로 본다 |
| Nextcloud 사용자가 `/remote.php/webdav/Documents/*.zip`을 내려받은 것을 '백업 파일 노출'로 잡음 | AIT wardbeck·wilson 웹서버·파일 공유 서버 | `WEBLOG_BACKUP_LEAK`: 파일 공유 앱 경로(`/remote.php/dav`·`webdav`, `/apps/files`, 공유 링크 내려받기)는 뺀다. 대신 훔친 계정으로 그 앱에서 받는 것은 이 규칙이 보지 않는다(규칙 명세의 '못 보는 것'에 적음) |
| RDS 관리자 비밀번호 재설정(`ModifyDBInstance`의 `masterUserPassword`)을 놓침 | Splunk `aws_credential_access_rds_password_reset` | 새 규칙을 만들지 않고 `CT_IAM_PERSISTENCE`(계정 조작, T1098)에 넣었다. `ModifyDBCluster`도 같다 |

## 이 숫자를 믿으면 안 되는 부분

- **보류용도 같은 계열이다.** AIT의 네 테스트베드는 같은 공격 시나리오 생성기로 만들었다. 보류용에서 오른 것은 "같은 공격을 다른 서버·날짜에서 다시 잡는다"는 뜻이지, CTF나 실제 고객 로그에서 오른다는 증거가 아니다.
- **줄 재현율은 dirb 줄 수가 거의 다 정한다**(wilson 42만 줄 중 dirb가 42만). 그래서 줄 재현율은 거의 안 움직인다. 단계 수가 더 의미 있다.
- **오탐 줄 일부는 라벨 빈틈이다.** AIT는 내부 인트라넷 서버에만 공격 라벨을 붙였다. 웹서버·파일 공유 서버에 남은 '오탐'에는 공격자 IP의 Nmap 스크립트 스캔이 들어 있다(라벨이 없을 뿐 실제 스캔). 이건 고치지 않았고, 고쳤다고 세지도 않았다.
- **harrison의 오탐 114줄은 그대로다.** 인트라넷 서버 108줄 중 92줄이 관리자 영역 접근, 12줄이 업로드 폴더 스크립트 요청이다. 개발용 wilson·wardbeck에서 본 같은 종류의 오탐은 업로드 폴더의 `*-225x300.php` 요청과, 공격자와 같은 IP(방화벽 주소)에서 온 사용자의 `/wp-admin/` 접근이었다. 업로드 폴더의 .php 요청은 실제 운영에서는 의심해야 할 모양이라 라벨에 맞추려고 끄지 않았다.
- **여전히 놓치는 것**: 웹셸 올리기(모든 AIT 테스트베드. wp-file-manager 취약점을 `POST /wp-admin/admin-ajax.php`로 한 번 쓰는 모양이라 일반 요청과 구별이 어렵다), 콘솔 로그인 실패 1~4건(10분에 5건 기준이라 일부러 안 잡음), 평소와 다른 도시·국가·사용자의 콘솔 로그인(기준선 규칙이 없음).
- **"과거부터 지금까지 모든 공격 데이터"는 아니다.** 이번에 쓴 것은 라벨이 붙은 공개 데이터 중 내려받을 수 있었던 것이다. 남은 후보: AIT-LDS 다른 테스트베드(rbd 등), Splunk attack_data의 AWS 밖 데이터, CSIC 2010(사이트가 응답하지 않았음).
