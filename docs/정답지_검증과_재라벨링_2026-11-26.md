# 줄 라벨이 없던 데이터의 정답지 점검과 다시 라벨하기 (2026-11-26)

**[확인]** = 결과 파일·로그 줄로 확인, **[추정]** = 확인하지 못한 판단.

## 결론

- 줄 라벨이 없던 데이터 4개(공방전, BOTSv3, EClog, 자체 lab)의 예전 정답지를 점검했다. **실행 기록으로 보장되는 것은 lab뿐**이고, 공방전·BOTSv3은 남이 쓴 해석(블루팀 보고서, 공식 질문의 답)을, EClog는 '표시 안 된 줄은 정상'이라는 가정을 정답으로 썼다.
- 그래서 AIT-LDS의 라벨 방식(줄마다 라벨과 그 라벨을 붙인 규칙 id, 근거가 없으면 붙이지 않음)으로 **모든 줄을 다시 라벨했다.** 라벨 스크립트는 LogSight 탐지 코드를 하나도 읽지 않는다. 엔진은 라벨을 다 만든 뒤 채점 스크립트에서 처음 돌렸다.
- 라벨마다 근거 줄(`evidence`)이나 근거 문자열(`evidence_text`)을 적었다. 근거로 판단할 수 없는 줄은 정상으로 두지 않고 **uncertain/unlabeled**로 따로 셌다.

### 공방전 정답지를 원본과 맞춰 보니 [확인]

블루팀이 보존한 WAF 원본(`attacker_evidence.tgz`의 `evt_waf.tsv`, 통합로그에 없던 관리형 규칙 이름이 있음)과 대조했다.

- **G1(71줄)**: 60줄은 AWS 관리형 규칙 `EC2MetaDataSSRF_BODY`(55)·`GenericRFI_BODY`(5)가 막은 요청이다. 내부 주소 조회 시도라는 근거가 줄에 있다. **나머지 11줄은 `BlockForwardedIP`**, 즉 블루팀이 출처 IP를 막아서 BLOCK된 것이라 요청 내용은 알 수 없다.
- **G2(29줄)**: 공격자 IP의 `/api/support/*` 요청이다. 서명 없는 토큰을 썼는지는 헤더가 로그에 없어 줄로 확인할 수 없다. 보고서 6장도 "테스트에서 서명 없는 토큰에 지원 권한을 넣자"라고만 적었다. 예전에 '탐지 6/29'로 센 6줄은 모두 `BlockForwardedIP`다. **엔진은 공격을 본 것이 아니라 블루팀의 IP 차단을 본 것이다.**
- **G3(2줄)**: 공격자가 직접 만든 작업(job-58154·58155)의 PDF 내려받기다. PDF가 내부 Recovery 주소를 렌더한 것이라는 보고서 내용은 로그에 없다.
- **G4~G6**: CloudTrail 줄 자체로 확인된다(EC2 인스턴스 역할 키를 AWS 밖 IP에서 사용, 실행 이름 `case-redteam-validation-002` 등).
- 통합로그의 WAF 432줄과 PageSnap 122줄은 **블루팀이 공격자 IP로 골라 낸 묶음**이었다(IPv6 2개를 빼면 전부 공격자 IP). 그래서 이 두 출처에서 '정상 줄'은 거의 없다. 예전 문서에 적지 않았던 선택 편향이다.

## 2. 다시 라벨한 방식

AIT-LDS v2.0 라벨 파일을 받아(`scripts/public/fetch_ait.py`) 형식을 확인했다. 한 줄 예:
`{"line": 1, "labels": ["attacker_http", "foothold", "dirb"], "rules": {"dirb": ["attacker.dirb.time"], ...}}`.
출처 라벨(attacker_http) + 단계 묶음(foothold) + 단계(dirb), 그리고 라벨마다 그것을 붙인 규칙 id다. 같은 꼴을 따랐다.

AIT는 공격자 실행 기록이 있어 '라벨 없는 줄 = 정상'이 성립한다. 우리 데이터에는 그 기록이 없으므로 두 가지를 바꿨다.

1. **공격자 식별자를 먼저 로그 줄 근거로 세운다.** 식별자마다 근거 줄을 `_summary.json`의 `anchors`에 적었다.
2. **정상도 근거 규칙이 있어야 붙인다.** 어느 쪽 근거도 없으면 `uncertain`(공방전)·`unlabeled`(BOTSv3·EClog)로 두고, 숫자는 빼거나 범위로 낸다.
