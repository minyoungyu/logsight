## 결론

- **판정(B 반, 규칙 보강 뒤 한 번만 잼): 맞게 탐지 24/56 = 43%(95% 31~56%). 목표 50%에 못 미쳐요.** Medium 이상만 보면 12/33 = 36%예요. [확인: `reports/public/panther_ct_B.json`]
- 보강 전 A 반은 20/64 = 31%였어요. A와 B는 서로 다른 규칙들이라 정확한 효과는 알 수 없어요. 구간이 겹쳐서 "좋아졌다"고 단정할 수도 없어요.
- 놓친 30개는 대부분 LogFinder에 아직 없는 영역이에요.

## 왜 이 데이터인가

- 기존 S6 계획(Splunk의 새 AWS 탐지 10개 이상)은 시작할 수 없었어요. security_content(689e177)에서 아직 안 잰 AWS 탐지가 4개뿐이에요.
- Stratus Red Team은 11/05 규칙 보강에 쓴 목록이고, Invictus(Stratus 데이터)도 이미 쟀어요. 그래서 처음 보는 데이터가 아니에요.
- Panther(`panther-labs/panther-analysis` e9c67b0, Apache-2.0)의 CloudTrail 규칙 시험 이벤트는 측정에 쓴 적이 없어요. 켜진 규칙 121개를 내용을 보기 전에 파일 이름 해시로 A(64)·B(56)로 나눴어요(`scripts/public/eval_panther.py`). 계획은 `reports/public/holdout_plan_2026-11-25.json` S6.panther에 있어요.

## 한계

- 시험 이벤트를 하나씩 넣어서, 반복·순서로 판단하는 LogFinder 규칙(10분 안 5건 등)은 걸릴 수 없어요. 그래서 숫자가 낮게 나와요.
- Panther 시험 이벤트는 사람이 만든 표본이라 실제 기록과 다를 수 있어요.
- B 반 명령을 확인하다가 한 번 실행했는데, 출력에서 숫자를 지워 반 이름만 봤고 결과를 저장하지 않았어요(A 결과 파일의 note).
- 정상 시험 표시(A 24/117, B 26/110)에는 실패한 시도, CI/CD 배포, 루트 계정 조회처럼 Panther와 기준이 다른 것이 섞여 있어요. AWS 쪽 오탐률로 바로 읽으면 안 돼요.
