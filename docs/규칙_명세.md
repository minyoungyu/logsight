## CT_LOGGING_TAMPER

**감사 로그·보안 서비스 중지·삭제** · defense-evasion · T1562.008 · 심각도 높음

- 로그: CloudTrail
- 조건: StopLogging, DeleteTrail, UpdateTrail, PutEventSelectors, DeleteFlowLogs, GuardDuty DeleteDetector·UpdateDetector, WAF DeleteLoggingConfiguration, Config 기록 중지·삭제, CloudWatch DeleteLogGroup, Route 53 Resolver 질의 로그 삭제·해제, Security Hub 끄기, Access Analyzer 삭제, Bedrock 호출 로그 끄기, LeaveOrganization(조직 통제 벗어나기) 호출 1건. 이름에 trail·log·audit가 든 버킷의 수명 주기 설정(로그 자동 삭제)도 포함
- 사각지대:
  - 로그 버킷 이름에 trail·log·audit가 없으면 수명 주기로 로그 지우기를 놓침
  - 로그를 끄면 그 뒤 기록이 없으므로, 끄기 전 기록이 있어야 걸림
- 오탐:
  - 운영자가 추적(trail) 설정을 바꾸는 정상 작업. 정상 작업 목록에 넣어도 '위험 설정'으로 남음
- 먼저 할 일: 누가 껐는지 확인하고 바로 다시 켠다. 끈 계정의 키를 의심한다.
- 검증: `tests/test_rule_validation.py` → `CT_LOGGING_TAMPER`

## CT_ROOT_USAGE

**루트 계정 사용** · initial-access · T1078.004 · 심각도 높음

- 로그: CloudTrail
- 조건: userIdentity.type이 Root인 호출 1건(AWS 서비스가 대신 남긴 AwsServiceEvent는 뺌)
- 사각지대:
  - 루트가 아닌 관리자 계정의 남용은 이 규칙으로 보지 않음
- 오탐:
  - 루트로만 할 수 있는 작업(결제, 계정 설정). 그 자체보다 '루트를 일상적으로 쓰는 습관'이 위험
  - 다른 행동(MFA 변경 등) 표본에서 루트 사용으로만 걸려 원래 행동을 가린 사례가 있음 [측정]
- 먼저 할 일: 누가 왜 루트를 썼는지 확인하고, 루트에 MFA를 걸고 루트 키는 지운다.
- 검증: `tests/test_rule_validation.py` → `CT_ROOT_USAGE`

## CT_IAM_PERSISTENCE

**IAM 사용자·키·권한 생성/변경** · persistence · T1098 · 심각도 높음

- 로그: CloudTrail
- 조건: CreateUser, CreateAccessKey, Create/UpdateLoginProfile, Attach/Put(User|Role)Policy, AddUserToGroup, CreateRole, UpdateAssumeRolePolicy, Create·SetDefaultPolicyVersion, 임시 연합 토큰(GetFederationToken), IAM Roles Anywhere 신뢰 앵커·프로필 생성, EC2 키 페어 생성·가져오기 호출 1건(성공·실패 모두)
- 사각지대:
  - 정책·그룹 삭제, SAML 공급자 변경은 보지 않음
  - 역할을 '외부 계정이 맡을 수 있게' 만든 것과 내부용 역할을 구별하지 않음
- 오탐:
  - 배포 도구(Terraform·CloudFormation)의 정상 IAM 변경. 배포 역할을 정상 작업 목록에 넣는다
- 먼저 할 일: 새로 생긴 사용자·키·권한이 의도한 것인지 확인하고, 아니면 키를 비활성화하고 권한을 되돌린다.
- 검증: `tests/test_rule_validation.py` → `CT_IAM_PERSISTENCE`

## CT_SG_OPENED

**보안그룹·네트워크 ACL을 0.0.0.0/0에 개방** · defense-evasion · T1562.007 · 심각도 높음

- 로그: CloudTrail
- 조건: AuthorizeSecurityGroupIngress 요청에 0.0.0.0/0이 들어 있음. 네트워크 ACL에 0.0.0.0/0 인바운드 허용 항목을 만들거나 바꾸는 호출(Create·ReplaceNetworkAclEntry)도 포함
- 사각지대:
  - IPv6 전체(::/0) 개방은 보지 않음
  - 네트워크 ACL 항목 삭제(DeleteNetworkAclEntry)로 막던 규칙을 없애는 것은 보지 않음
  - 포트를 가리지 않음(80/443 공개와 22 공개를 같게 취급)
- 오탐:
  - 웹 서버의 80/443 공개처럼 의도한 개방. 정상 작업 목록에 넣으면 '위험 설정'으로 표시
- 먼저 할 일: 어떤 포트가 열렸는지 보고, 관리 포트(22·3389)면 바로 닫는다.
- 검증: `tests/test_rule_validation.py` → `CT_SG_OPENED`

## CT_S3_PUBLIC

**S3 버킷을 인터넷 전체 또는 다른 계정에 공개(ACL·정책)** · exfiltration · T1537 · 심각도 높음

- 로그: CloudTrail
- 조건: PutBucketAcl·PutObjectAcl·PutBucketPolicy 등에서 AllUsers·AuthenticatedUsers 권한, public-read(-write) ACL, Principal '*' 허용 정책이 들어 있음. 퍼블릭 액세스 차단을 지우거나 끄는 호출도 포함. 버킷 정책이 우리 계정이 아닌 계정 ID를 허용하는 경우도 포함
- 사각지대:
  - 정책에 조건(Condition)이 붙어 실제로는 제한된 경우도 공개로 봄
  - 공개된 뒤 외부인이 파일을 올리거나 읽은 것은 S3 접근 로그가 필요해 보지 않음 [측정]
  - 복제 설정으로 다른 계정에 복사는 보지 않음 [측정]
  - 다른 계정이 우리 조직 계정이어도 외부로 봄(조직 계정 목록을 모름)
- 오탐:
  - 정적 웹사이트 호스팅 버킷처럼 일부러 공개한 경우
- 먼저 할 일: 공개가 의도한 것인지 확인하고, 아니면 버킷의 퍼블릭 액세스 차단을 켠다.
- 검증: `tests/test_rule_validation.py` → `CT_S3_PUBLIC`
