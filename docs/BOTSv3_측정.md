# 실제 AWS 로그로 잰 결과 (Splunk BOTSv3)

지금까지의 측정(자체 lab, 공방전, AIT-LDS)은 우리가 만든 환경이거나 AWS가 아닌 로그였다.
여기서는 **남이 실제 AWS 계정에서 만든 로그**로 같은 엔진을 잰다. 측정은 규칙만 쓴다(AI 호출 없음).

## 한눈에 보기

| | 고치기 전(main) | 고친 뒤 |
|---|---|---|
| 읽은 이벤트 | 195,829건 (SSH 4줄, GuardDuty 0건) | 195,872건 (SSH 46건, GuardDuty 1건) |
| 사건 수 | 47 | 48 |
| 목록 없이 판정 | 47건 모두 "공격" | 공격 7, 위험 설정 41 |
| 직원 목록을 넣은 판정 | 공격 44, 정상 3 (**버킷 공개·보안그룹 개방이 "정상"**) | 공격 3, 위험 설정 43, 정상 2 |
| B1 유출 키 악용 | 탐지 | 탐지 |
| B2 S3 버킷 공개 | **놓침** | 탐지 (목록 넣으면 "위험 설정"으로) |
| B3 외부인의 버킷 파일 업로드 | **놓침** | **놓침** (S3 접근 로그 미지원) |
| GuardDuty가 낸 결과 | 1건(포트 탐색, 낮음) | 같음 |

**결론:** 실제 AWS 로그에서 큰 사건 두 개(유출 키, 버킷 공개)는 잡지만, 처음 그대로는 버킷 공개를 놓쳤고 판정이 전부 "공격"이라 쓸 수 없었다.
측정하면서 파서·규칙 결함 5개를 고쳤으므로, 이 표의 "고친 뒤"는 **데이터를 보고 고친 결과**다. 독립 측정 점수로 쓰면 안 된다.
같은 기간 GuardDuty는 유출 키와 버킷 공개 어느 것도 결과로 내지 않았다(아래 4절의 한계 참고).

## 1. 데이터

- **BOTSv3** (Boss of the SOC v3, Splunk, 2018-08-20 하루). 가상 회사 Frothly의 실제 AWS 계정·서버·PC에서 공격과 정상 업무를 함께 기록했다.
  - 출처: <https://github.com/splunk/botsv3> (CC0 공개 도메인). 받은 파일: `botsv3_data_set.tgz` (S3 공개 버킷).
  - 정답 기준: 공식 질문과 공개 풀이(GitHub `DelfinoRT` 실습 기록, cybersecurityfreeresource 풀이). 데이터셋에 줄 단위 라벨은 없다.
- Splunk 색인 형태로만 배포되어, Splunk 없이 원본 로그 형식으로 꺼내는 해석기를 만들었다.
  - `python scripts/public/botsv3_extract.py <db 폴더> <출력 폴더>`
  - 꺼낸 것: CloudTrail 6,571건, VPC Flow 183,354줄, ALB 2,051줄, auth.log 350줄, 웹서버 access.log 3,907줄, GuardDuty 결과 1건.
  - 데이터는 저장소에 넣지 않는다.
- 재현: `python -m logsight analyze <출력 폴더> --year 2018 --no-ai`
  - 직원 목록: `{"known_activity":[{"label":"직원 IAM 사용자","actors":["bstoll","btun","splunk_access"]}]}` (공개 풀이에 나온 직원·연동 계정)

## 2. 공격 단계별

AWS 로그로 볼 수 있는 단계만 셌다. PC의 코인 채굴, 사내 서버 침해, O365는 AWS 로그 밖이라 뺐다.

| 단계 | 무엇이 있었나 | 결과 | 걸린 규칙 |
|---|---|---|---|
| B1 | 공개된 IAM 키를 외부에서 사용. 권한 거부가 몰리고 키 생성·인스턴스 생성을 시도(실패) | 탐지 (사건 1개, 233건) | CT_ACCESS_DENIED_BURST, CT_IAM_PERSISTENCE |
| B2 | 직원이 콘솔에서 S3 버킷 ACL을 바꿔 인터넷 전체에 공개 | 탐지 (고친 뒤) | CT_S3_PUBLIC (새 규칙) |
| B3 | 공개된 버킷에 외부인이 파일을 올림 | **놓침** | S3 접근 로그를 읽지 않음 |

B1에서 같은 키가 다른 도구(ElasticWolf)로 다른 IP에서 2번 쓰인 기록은 사건에 들어가지 않았다. 둘 다 거부됐지만 2건뿐이라 권한 거부 규칙의 기준에 못 미쳤다.
B1의 인스턴스 생성 시도 576건은 모두 실패해서 '인스턴스 대량 생성' 규칙(성공만 셈)에는 걸리지 않고 권한 거부 규칙으로 잡혔다. 보고서는 이 사건을 "시도는 모두 막힘, 급하지 않을 수 있음"으로 설명한다.

## 3. 측정이 드러낸 결함과 고친 것

| # | 결함 | 고친 것 |
|---|---|---|
| 1 | EventBridge로 받은 GuardDuty 결과(키가 camelCase)를 통째로 버림 | 키 이름을 바꿔 같은 파서로 읽음 |
| 2 | auth.log의 `Invalid user` 줄을 안 읽어 350줄 중 4줄만 이벤트가 됨 | 실패로 셈(같은 시도의 Failed 줄과 중복 제거). SSH 무차별 대입이 잡힘 |
| 3 | S3 버킷 공개(ACL·정책)를 잡는 규칙이 없음 | CT_S3_PUBLIC 추가. 요청 원문이 길어 잘리기 전에 판단 |
| 4 | 외부 서버의 **응답**(443·8088 → 임시 포트)을 포트 스캔으로 셈 | 응답 방향 흐름은 스캔에서 뺌 |
| 5 | 인터넷 스캐너가 열린 SSH 포트를 두드린 기록 40여 건이 모두 "공격" | 다른 행동이 없으면 "위험 설정(포트를 닫으세요)"으로 |

판정 규칙도 두 가지 바꿨다.

- 정상 작업 목록의 계정이 한 일이라도 **위험한 설정 변경**(버킷 공개, 보안그룹 개방, 로그 끄기, 스냅샷 공유)이면 "정상"이 아니라 "위험 설정"으로 둔다. 고치기 전에는 직원이 버킷을 공개한 사건이 "정상"으로 묻혔다.
- 정상 작업 목록의 계정이라도 **키 유출 징후**(권한 거부 폭주, 한 키를 여러 곳에서 사용)가 있으면 "판단 불가"로 둔다. 유출된 계정(web_admin)을 목록에 넣고 돌리면, 고치기 전 규칙으로는 B1이 "정상"이 됐다.

고친 뒤에도 공방전 측정 점수는 그대로다(규칙 판정 4/7, 정상 작업 목록 포함 6/7).

## 4. 오탐과 한계

- 목록 없이 "공격"으로 남은 7건 중 실제 공격은 3건(B1, 인터넷 SSH 무차별 대입, SQL 인젝션 시도 1건)이다. 2건은 직원의 위험 설정(B2, 보안그룹 개방), 2건은 직원 로그인·Splunk 연동 계정의 목록 조회다. 직원 목록을 넣으면 공격 3건만 남는다.
- B3를 보려면 S3 서버 접근 로그(또는 CloudTrail S3 데이터 이벤트) 파서가 필요하다. 아직 없다.
- GuardDuty 결과가 1건뿐인 것은 2018년 GuardDuty 기준이고, 데이터셋이 결과를 전부 담았는지 확인할 수 없다. "GuardDuty는 이걸 못 잡는다"의 근거로 쓰지 않는다.
- 하루치, 계정 하나다. 일반화된 성능 숫자가 아니라 **실제 AWS 로그에서 엔진이 깨지는 곳을 찾은 기록**으로 읽어야 한다.
