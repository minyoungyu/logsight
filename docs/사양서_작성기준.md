# 사양서 작성 기준 (2026-11-26)

[사양서.md](사양서.md)를 쓰고 고칠 때 지키는 규칙이다. 지금까지 판마다 흩어져 있던 기준(사양서 0·3·8·9절, 체크리스트 1절, 외부비교 머리말)을 한곳에 모으고,
비어 있던 것 세 가지를 새로 정했다. **(1) 목표 숫자마다 근거 유형을 밝힌다. (2) 상태 기호를 기능과 성능으로 나눠 정의한다. (3) 사양서의 측정 숫자는 근거 파일이 없으면 CI가 막는다.**

이 문서의 숫자는 저장소 결과 파일, 직접 다시 돌린 계산, 그리고 2026-11-26에 원문을 열어 확인한 외부 문서에서만 가져왔다. 근거를 찾지 못한 것은 "기록 없음"으로 적었다.

## 1. 참고한 외부 기준

비슷한 탐지 도구의 규칙·사양 형식과 AWS 공식 문서를 원문으로 확인했다(2026-11-26).

## 2. 요구사항 한 줄을 쓰는 규칙

| 규칙 | 내용 | 확인 방법 |
|---|---|---|
| R1 하나만 | 한 행에 요구사항 하나. "그리고"로 두 기능을 묶지 않는다 | 검토 |
| R2 통과/실패로 가름 | '받아들이는 기준'은 숫자·금지 문구·화면 크기·파일 존재처럼 두 사람이 같은 판정을 내릴 수 있게 쓴다. "쉽게", "빠르게"만 있으면 안 된다 | 검토, TC 작성 가능 여부 |
| R3 추적 | FR·NFR마다 TC가 하나 이상. 자동 TC는 `tests/파일.py::이름`을 적는다 | `scripts/spec_trace.py`(CI) |
| R4 목표 숫자에 근거 유형 | 목표 숫자를 새로 쓰거나 바꾸면 3절 표에 근거 유형(아래)을 적는다 | 검토 |
| R5 측정 숫자에 근거 파일 | '지금' 칸의 측정 숫자는 [근거_목록.json](근거_목록.json)에 결과 파일과 함께 등록. 파일이 없으면 `spec_unbacked`에 이유를 적는다 | `scripts/evidence_check.py`(CI) |
| R6 개발 점수 분리 | 그 데이터를 보고 규칙을 고친 뒤의 점수는 '개발 점수'라고 적고 목표 달성으로 세지 않는다 | 검토, 4절 상태 규칙 |

| R8 ID는 다시 쓰지 않음 | `S번호`, `FR-번호`, `NFR-번호`, `TC-<영역>-<번호>`. 지운 ID의 번호는 비워 둔다 | 검토 |
| R9 바꾼 이유를 남김 | 숫자·상태를 바꾸면 8절 변경 기록에 전과 후, 이유를 적는다 | 검토 |

**목표 숫자의 근거 유형(R4)**

- **외부**: 열어서 확인한 공식 문서나 원문. 링크와 확인한 날짜를 적는다.
- **측정**: 저장소 결과 파일의 기준선(지금 값). 파일 경로를 적는다.
- **계산**: 다른 숫자에서 식으로 나온 값. 식을 적는다.
- **팀 결정**: 위 셋이 없을 때. 누가 언제 정했는지 적는다. 근거가 없다는 것을 숨기지 않는다.

## 3. 목표 숫자별 산정 근거

목표 값 자체를 고른 이유는 대부분 **기록에 없다**. 아래 근거는 지금 확인할 수 있는 것을 근거 유형별로 모은 것이다. 이 근거들이 목표를 정당화하는지, 아니면 값을 바꿔야 하는지는 팀이 정할 일이다.
각 줄의 [측정]·[계산]·[외부]는 2절의 근거 유형이다. 구간은 모두 95% 윌슨 구간이다.

### T1. 정상 웹 요청 오탐 0.1% 이하 (S7, NFR-12)

- 기록: v1.0(11/20)에 처음 나옴. 0.1%를 고른 이유는 **기록 없음**.
- [측정] 처음 본 실제 로그(EClog 하루치)의 지금 값은 라벨 보정 0.496%(1,740/350,674줄)다(`reports/public/reallog_eclog_1day.json`).
- [계산] 부담으로 바꾸면: 그 하루치는 350,683줄이다. 0.1%면 하루 약 351줄, 지금 값이면 1,740줄이 표시된다. 표시된 줄이 사건 몇 개로 묶이는지는 재지 않았다.
- [계산] 판정 가능성(R7): 35만 줄이면 0.1%의 구간이 0.090~0.111%라 목표 달성 여부를 가릴 수 있다. 서버 하나(7,969줄)로 재면 0.051~0.198%라 가릴 수 없다. 그래서 단위는 "정상 라벨 요청 줄, 서버 합"이고, 표본은 10만 줄 단위 이상이어야 한다.
- 판정: 측정 단위와 표본 크기는 근거가 있다. **0.1%라는 값은 팀 결정**이다. 대안은 "하루 표시 줄 N개 이하"처럼 사용자가 겪는 부담으로 다시 쓰는 것이다.

### T2. 처음 본 AWS 데이터 50% 이상 (S6, NFR-11)

- 기록: v1.0에 "목표"로 처음 나옴(그때 31%). 50%를 고른 이유는 **기록 없음**.
- [측정] 기준선은 31%(16/52, `reports/public/splunk_attack_data.json`)이고, 구간은 19.9~44.3%다. 50%는 이 구간보다 위라서, 50%를 넘으면 우연이 아닌 개선이라고 말할 수 있다.
- [계산] 판정 가능성(R7): Panther B 반처럼 표본이 56개면 하한이 50%를 넘으려면 36/56(64%) 이상이어야 한다. 지금 24/56(43%, 30.8~55.9%)은 목표 미달이고, 구간이 50%를 포함해서 "확실히 미달"이라고도 할 수 없다.
- 판정: **50%는 팀 결정**이다. 기준선과 비교하는 근거는 있다.

### T3. 판정 재현율 90%, '공격 의심' 정밀도 80%, 사건 30개 이상 (S1, NFR-20)

- 기록: v2.0(11/20)에 Claude가 썼다. 값의 이유는 **기록 없음**.
- [계산] 공격 20개면 90%는 2개까지 놓쳐도 된다는 뜻이다. 지금 19/20(95%)의 구간은 76.4~99.1%다. 그래서 개발 세트로는 "90% 이상"을 통계적으로 말할 수 없다.
- [계산] 20개를 모두 맞혀도 하한은 90%에 못 미친다. **공격 사건 35개를 모두 맞혀야** 하한이 90%를 넘는다. 30개라는 최소 수는 그 기준보다 작다.
- 재현율이 정밀도보다 높은 이유: 놓친 공격이 오탐 하나를 확인하는 것보다 비싸다는 판단으로 보인다(사양서 1절 "판정이 맞다"). 하지만 이를 적은 **기록은 없다**.
- 판정: **팀 결정**이다. 독립 라벨 데이터로 잴 때 사건 수는 35개 이상을 권한다.

### T4. 공격 단계 80% 표시 (S2), 원인 설정 80% 지목 (S5)

- 기록: v2.0에 처음 나옴. 이유는 **기록 없음**.
- [계산] 단계 수가 작아서 80%는 실제로는 정수 개수다. 공방전 6단계면 5단계(83%)부터, AIT 7단계면 6단계(86%)부터 통과한다. 지금 처음 본 AIT는 3/7·4/7이라 미달이다(`reports/public/ait_russellmitchell.json`, `reports/public/ait_fox.json`).
- 판정: **팀 결정**이다. 사양서에는 "단계 수 − 1개까지 놓쳐도 됨"처럼 정수로 쓰는 편이 오해가 적다.

### T5. 비전문가 이해: 8명 이상, 6명 이상이 같거나 높고, 차이 중앙값 +2점, 평균 7/10 (S3)

- [기록] 8명은 교차 설계에서 조건 순서를 맞추려고 4의 배수로 정했다([설계](사용자평가/설계.md) 2절).
- [계산] +2점은 10점 만점(문항 5개 × 0~2점, [채점기준](사용자평가/정답_채점기준.md))에서 문항 하나를 완전히 더 맞힌 만큼이다.
- [계산] 6/8 기준의 통계적 의미: LogFinder가 효과가 없어도(반반) 8명 중 6명 이상이 같거나 높게 나올 확률은 14.5%(37/256)다. 7명 이상이면 3.5%, 8명이면 0.4%다. 그래서 6/8은 "효과가 있다"는 통계적 증거가 아니다. 설계 문서도 p값은 참고로만 적는다고 했다.
- 평균 7/10, 6명이라는 값의 이유: **기록 없음**.
- 판정: 인원은 근거가 있고, 통과선은 **팀 결정**이다. 증거로 쓰려면 7/8 이상을 기준으로 삼는 것을 검토할 만하다.

### T6. 경보 뒤 30분(분석 15분 + 판단 15분), 늦어도 1시간, 경보→통지 15분 (1절, S4, NFR-03)

- [기록] 30분은 분석 15분과 판단 15분의 합이다(사양서 1절). 15분 각각의 이유는 **기록 없음**. 1시간은 v2.0에서 Claude가 정했고, 문서 댓글로 확인을 물었지만 **답이 없다**.
- [외부] CloudTrail은 API 호출 뒤 평균 약 5분 안에 로그를 전달한다. GuardDuty의 새 결과는 EventBridge로 near real-time 전달된다. 그래서 15분 예산 가운데 로그가 도착하기까지 약 5분이 쓰인다.
- [측정] 분석 자체는 예산보다 훨씬 짧다. 1만 건은 0.6초, 194만 건(flaws.cloud)은 2분 3초다(`reports/remeasure_2026-11-26/spec/bench_10k.json`, `reports/remeasure_2026-11-26/flaws/run.json`).
- 판정: '분석 15분'은 외부 지연과 측정으로 여유가 있다고 말할 수 있다. **판단 15분과 1시간 상한은 팀 결정**이다. 실제 사람 시간은 S3에서만 잴 수 있다.

### T7. 같은 경보는 60분 안에 다시 분석하지 않음 (FR-13), 로그 끊김 5분 (FR-20)

- 기록: 이유는 **기록 없음**.
- [외부] GuardDuty가 같은 결과의 반복을 묶어 보내는 주기는 15분, 1시간, 6시간(기본) 가운데 고른다. 60분은 그중 하나와 같다. 다만 그 때문에 60분으로 정했다는 기록은 없다.
- 판정: **팀 결정**이다.

### T8. 처리 시간과 메모리: 1만 건 10초, 20만 건 30초, 194만 건 5분, 20만 건 500MB (NFR-01·02·04)

- [측정] 194만 건은 flaws.cloud 공개 데이터의 실제 이벤트 수(1,939,207건, `reports/remeasure_2026-11-26/flaws/report.json`)다. 1만·20만 건과 시간·메모리 상한의 이유는 **기록 없음**. v1.0은 "지금 코드 기준"으로 썼고, 그때 측정값이 모두 상한 안에 있었다.
- 주의할 점: NFR-04의 165MB는 파이썬이 잡은 메모리(tracemalloc)다. 194만 건 재측정의 2,669MB는 프로세스 전체(RSS)라서 둘은 단위가 다르다(`reports/remeasure_2026-11-26/spec/bench_200k.json`의 memory_note).
- 판정: **팀 결정**이다. 메모리는 측정 방식을 하나로 정해야 한다.

### T9. AI 분석 1회 $0.50 이하 (NFR-17)

- 기록: v2.0에서 Claude가 정했고, 문서 댓글로 확인을 물었지만 **답이 없다**. v1의 "사건 1건 100원"에서 바꾼 이유(실제 모델과 맞지 않음)는 기록돼 있다.
- [측정] 10/26 공방전은 $0.20이었다(`reports/ctf/gongbang_ai.json`). 11/26 재측정 6회는 사건 8개로 $0.28~$0.31이다. 가격은 사양서 5절의 단가(입력 $4·출력 $20, 100만 토큰당)로 계산했다.
- 판정: **팀 결정**이다. 지금은 상한의 약 60%를 쓴다. 사건 30개(NFR-05 상한)일 때의 비용은 아직 재지 않았다.

### T10. 화면 1366×768, 390×844 (NFR-22)

- 기록: 이유는 **기록 없음**.
- [외부] Playwright의 기기 목록에서 iPhone 12·13·14의 화면(screen)은 390×844다. 그런데 브라우저가 실제로 보여 주는 영역(viewport)은 390×664다. 지금 검사는 844를 기준으로 하므로 실제보다 느슨하다. 다만 11/26 측정에서 두 요소의 아래 끝은 휴대폰에서 최대 586px라서 664 기준으로도 통과한다(`reports/remeasure_2026-11-26/spec/first_screen.json`).
- 1366×768이 흔한 노트북 해상도라는 근거는 이번에 원문으로 **확인하지 못했다**.
- 판정: 휴대폰 높이는 664로 고치는 것을 권한다. 노트북 크기는 **팀 결정**이다.

## 4. 상태 기호 (✅ / 🟡 / ⬜)

Sigma가 규칙의 `status`를 "운영에 써도 되나"로 나누듯, 상태는 **이 숫자를 믿고 써도 되나**로 정한다. 기능과 성능은 따로 판정한다(FR ✅ 옆에 "(S6 ⬜)"처럼 함께 적는다).

| 기호 | 기능(FR) | 성공 기준(S)·성능(NFR) |
|---|---|---|
| ✅ | 기능이 있고, 받아들이는 기준을 자동 테스트가 확인 | 처음 본 데이터나 실환경에서 목표 달성(처리 시간·메모리처럼 정확도가 아닌 NFR은 합성 부하 측정도 인정) |
| 🟡 | 기능은 있지만 실계정·실데이터 확인이 부족(가짜 AWS만, 실계정 1회 등) | 개발 데이터나 가짜 환경에서만 목표 달성, 또는 표본이 작아 구간이 목표를 가로지름 |
| ⬜ | 미구현 | 처음 본 데이터에서 미달, 또는 아직 측정 안 함 |

- 건너뛴 테스트는 통과가 아니다. CI는 `LOGSIGHT_NO_SKIP=1`로 돌고, 회차 결과는 `scripts/checklist_run.py`가 만든다(NFR-21).
- 이 규칙으로 v2.4에서 S2(처음 본 AIT 3/7·4/7)와 S4(판단 시간 미측정)를 ⬜로 바꿨다. 11/21 재평가가 지적한 정의 충돌("🟡는 개발 데이터만이어도 목표를 넘으면"과 "개발 점수는 달성으로 세지 않음")을 이렇게 풀었다.

## 5. 측정 숫자와 근거 파일 (`scripts/evidence_check.py`)

CI(`tests/test_evidence.py`)에서 세 가지를 본다.

1. **근거 목록의 항목마다** 결과 파일이 있는지, 파일에서 다시 계산한 값이 같은지, 문서에 그 문구가 그대로 있는지 본다. 계산 종류는 다음과 같다.
   - 값 비교, 개수, 판정 분포
   - 서버 합·서버 하나의 오탐 줄과 비율
   - 공격 단계 표시 수
   - 비율(%)
   - 95% 윌슨 구간
   - 여러 파일의 합
   - 토큰 × 단가 비용
2. **문서의 `reports/...` 경로**가 실제로 있는지 본다. 명령 예시 경로는 `path_allowlist`에 이유와 함께 적는다.
3. **사양서 S·NFR 표 '지금' 칸의 측정 숫자마다**(범위·%, 분수, 초·분, MB, $) 사양서를 가리키는 근거 항목의 quote 안에 있는지, 아니면 `spec_unbacked`에 이유와 함께 있는지 본다.
   - 둘 다 아니면 실패한다. `spec_unbacked`에 적었는데 사양서에서 사라진 숫자도 실패한다.
   - 10/xx·11/xx 꼴의 분수는 이 프로젝트 기간의 날짜로 보고 뺀다. "95% 구간"의 95%는 신뢰수준이라 뺀다.
   - 숫자를 바꾸면 근거 항목의 quote도 같이 바꿔야 통과한다.

**지금 결과(2026-11-26):** 근거 항목 62개, 그중 사양서 36개, 문제 0건이다. 근거 파일이 없는 사양서 숫자는 3개다.

| 행 | 숫자 | 파일이 없는 이유 |
|---|---|---|
| S6 | 36~80% | 9/15에서 계산한 구간. 결과 파일에 구간 필드가 없음 |
| NFR-02 | 1분 41초 | GitHub Actions 로그의 값. 결과 파일을 남기지 않음. 11/26 재측정(2분 3초)은 파일 있음 |
| NFR-03 | 0.6초 | `docs/시연_실계정.md`에 붙인 명령 출력뿐(가짜 AWS) |

**검사가 잡지 못하는 것:** 측정 숫자가 아닌 개수("319개 중 4개" 같은 '개' 단위)는 자동 추출 대상이 아니다. 그래서 근거 항목을 따로 등록했다. 사양서 밖 문서(README, 측정 문서)는 등록한 항목만 검사한다.

## 6. 고칠 때의 순서

1. 측정을 다시 하면 결과를 `reports/` 아래 JSON으로 남긴다. 화면에만 찍고 끝내지 않는다. 이번에 `verdict_eval.py`, `fix_eval.py`, `bench.py`, `regress_splunk.py`, `first_screen_check.py`를 모두 `--json`으로 남길 수 있게 했다.
2. 사양서 '지금' 칸을 고치고, 근거 목록의 quote와 값을 함께 고친다.
3. 목표를 바꾸면 3절에 근거 유형을 적고, 8절 변경 기록에 이유를 남긴다.
4. `python scripts/evidence_check.py`, `python scripts/spec_trace.py`, `python -m pytest`를 돌린다.
